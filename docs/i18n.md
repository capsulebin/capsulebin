# Interface languages

Every page of CapsuleBin exists once per interface language. The web interface is available in
English and German, and every instance offers both. The pages of the instance's default language
have no path prefix (`/p/{id}`); every other language lives under its prefix (`/de/p/{id}`). The
operator chooses only which language is the default (`[i18n] default_language`, `en` unless set).
Each language's shells are generated at build time from one set of templates and a catalogue per
language, and each shell loads the catalogue of its own language only: nothing is translated at
runtime, nothing is loaded afterwards and nothing flickers.
The server does not look at the browser's language. A head script in every shell moves the page
to the user's own choice, else to the browser language, else to the default. The CLI, the API's
`problem+json` texts and the legal texts are English (see [Limits](#limits-and-open-points)).

## Rules

### Languages

Known languages: `en`, `de` (`KNOWN_LANGUAGES`, in this order). Codes are exact and lowercase.
Every known language is always offered; which ones are offered is not configurable.

The default language `D` is `[i18n] default_language` (env
`CAPSULEBIN__I18N__DEFAULT_LANGUAGE`), `en` unless set. It is the only key in `[i18n]`: a code
that is not a known language, or any other key in the table (`languages`, …), is a startup error
naming the key.

### Routes

`<prefix>` is empty for the default language `D` and `/L` for every other known language `L`:

| Path | Answer |
| --- | --- |
| `<prefix>/` | Create page (`index.html`) |
| `<prefix>/p/{id}` | View page (`p.html`) |
| `<prefix>/manage/{id}` | Management page (`manage.html`) |
| `<prefix>/report` | Report form (`report.html`) |
| `<prefix>/imprint`, `<prefix>/privacy`, `<prefix>/terms` | Legal page (`legal.html`) if it is served here, otherwise the generic `404` |
| `/L` (not the default) | `302` to `/L/`, query kept |
| `/D`, `/D/`, `/D/p/{id}`, … (every page path under the default language's prefix) | `302` to the same path without the prefix, query kept (`/D` → `/`) |

So with the default `en`, `/p/{id}` is the English page, `/de/p/{id}` the German one and
`/en/p/{id}` a redirect to `/p/{id}`; with `default_language = "de"` German is prefix-less,
English is under `/en/` and `/de/p/{id}` redirects.

Every shell answers `200`, `text/html; charset=utf-8`, `Cache-Control: no-store`, with
`<html lang>` of its language.

The redirects carry `Cache-Control: no-store` (a changed default language takes effect at once)
and an absolute path without `public_url` as `Location`. They copy the path without looking at it,
so the answer does not depend on whether an id exists and triggers no retrieval; the fragment with
the key is never sent and stays in the browser. The legal paths under `/D/` redirect even when the
page is not configured, so the redirect depends on the path alone; the `404` then comes from the
prefix-less path.

**The server does not negotiate.** `Accept-Language` changes no answer and no response carries
`Vary: Accept-Language`: a path alone decides which shell is served.

A prefix that is not a known language (`/fr/`, `/xx/p/{id}`, `/DE/`) gets the same generic `404`
as any unknown path. The API (`/api/…`), `/health/*` and static assets (`/assets/…`,
`/language-init.js`, `/theme-init.js`) have no prefix. A `*.html` path (`/de/index.html`) is never
served directly: a shell served that way would lack the token and marker replacement.

### Choosing the language in the browser (`language-init.js`)

`public/language-init.js` runs in the `<head>` of every shell before anything is shown. The
language of the current path is its first segment if that is an offered language, otherwise the
default language. The script determines the wanted language in this order:

1. `localStorage` `capsulebin.language`, if that language is offered;
2. the first entry of `navigator.languages` whose primary subtag is offered;
3. the default language (`data-default` of the languages meta element).

If the result differs from the language of the path, it calls `location.replace` with the same
path in the wanted language — no prefix for the default language, `/<lang>` otherwise — plus
query and fragment, unchanged. Without the meta element, with a `data-default` that is not an
offered language, without `localStorage` or on any exception, it does nothing.

The document it replaces is never styled. So that it is not painted as a bright default canvas in
dark mode, every shell declares `<meta name="color-scheme" content="light dark">` before the head
scripts, and `theme-init.js`, which runs first, narrows it to a stored `light` or `dark` choice.
Once the stylesheet applies, `color-scheme` in `tokens.css` takes precedence over the meta.

Examples on an instance with the default `en`: a German browser opening a share link
`/p/<id>#v1.…` lands on `/de/p/<id>#v1.…` and decrypts there; an English browser without a stored
choice following `/de/p/<id>#v1.…` lands on `/p/<id>#v1.…`, and stays on `/de/…` once German was
chosen in the switch.

### Language switch

In the header of every page, next to the theme toggle: one button per offered language, labelled
with its own name ("English", "Deutsch", from `Intl.DisplayNames`), the page's language marked
with `aria-current`, in the order of the meta element. Hidden when only one language is offered.

A choice stores `capsulebin.language` and loads the same path (query and fragment included) in
the chosen language — prefix-less for the default language — with `location.replace`, so the old
address does not stay behind as a history entry. Exception: once a page must not be reloaded, the
switch only stores the choice and says next to it that it applies from the next page on. That
point is

- on the view page: the user's go-ahead for the retrieval — the click that confirms the burn
  warning or submits the password. A capsule that needs neither is retrieved without a click; for
  it the point is right before the retrieve request, after the key derivation
  (`OpenHooks.beforeRetrieve` in core, called with nothing asynchronous between it and the
  request);
- on the management page: when the deletion is confirmed;
- on the report form: the first input into any of its fields;
- on the create page: as soon as the form holds any user input — an item with content (text or a
  file) or a name the user typed, or any other field changed from its default (title, password,
  expiry, burn and the other options). It stays so if the form is emptied again, and on the page
  that shows the new links. On an untouched form the switch navigates.

Once store-only, the switch stays so for the rest of the page.

The other way round, a choice that navigates marks the page as being left (`isLeavingPage`): the
old document stays on screen until the new one arrives, so the switch disables every button and
form field in `<main>`, and the view and management pages start no retrieval or deletion from it.
A burn confirmation, a password or a delete confirmation given in that gap does nothing; the
automatic retrieval asks the same question in `beforeRetrieve`, and if the page is being left,
`openPaste` ends with `aborted` without sending `/retrieve`. Whichever comes first wins: either
the page is reloaded in the other language and nothing was sent, or the action runs and the choice
applies from the next page.

The notice appears in the **chosen** language, not the page's (and is marked with that `lang`). It
is the one text every page holds in every language, see [Catalogue modules](#catalogue-modules).

### Links

- Internal links in the shells and the pages (logo, "Create another", "Cancel", "Report content",
  the report link with `?id=` on the view page) point to the page's own language: no prefix on a
  page in the default language, `/L/…` otherwise.
- Footer links to legal pages served here follow the same rule (`/imprint`, `/de/imprint`); so do
  links in the built-in legal texts to the privacy notice and the report form. Targets configured
  as `url` and links in the operator's Markdown stay as written.
- Share and management links created by the client have **no** prefix
  (`<origin>/p/<id>#v1.…`): they open in the default language, and the recipient's browser moves
  to its own language. The CLI prints them the same way.
- `parseLink` in core drops a known language segment directly before `p`/`manage`
  (`https://x.example/de/p/<id>#…`) from `base`, so the CLI works with a link copied from the
  address bar. Any other segment, including an unknown two-letter one (`/cb/p/<id>`) or
  `de-AT`/`DE`, stays part of `base`.

### Base URLs (`server.public_url`, CLI `--server`)

No link is created on a base that a client could misread. The server refuses such a
`server.public_url` at startup (also from `capsulebin check`); CLI `put` refuses such a
`--server`/`CAPSULEBIN_SERVER` with a usage error (exit code `2`, nothing sent). `get` and
`delete` take the base from the link and have no such check. Both sides apply the same rules,
checked against the shared vectors in `src/core/tests/fixtures/base-language.json` — that is the
whole compatibility guarantee for links with a path in front of `p`/`manage`.

1. **Must parse as an http(s) URL.** A `server.public_url` the `url` crate cannot parse
   (`https://exa mple.org/team/de`, `https://`, `http://example.org:port`) is a startup error
   ("not a valid URL"); CLI `put` answers "must be an http(s) URL".
2. **No query or fragment, also no empty one** (`…/team?lang=/de`, `…/team#/de`, `…/team?`,
   `…/team#`, `https://example.org?`): request paths and links are appended to the base as text and
   would end up inside them. The check runs on the base as given, before a trailing slash is
   removed (`…/team?x=1/`), and before the language rule. A percent-encoded `%3F` or `%23` is path
   and accepted. (`has_query_or_fragment` / `hasQueryOrFragment`, vectors `query_or_fragment`.)
3. **The path must not end in a known language code**, whichever is the default: `parseLink` would
   read `https://example.org/team/de/p/<id>` as the `/de/` prefix and address the shortened base.
   The rule takes the path as the WHATWG URL parser normalizes it — dot segments resolved, also
   percent-encoded ones (`%2e`), `\` read as `/` —, then its last non-empty segment, compared
   exactly with the known codes. Refused: `/de`, `/team/en`, `/team/de/`, `/team/de/.`,
   `/team/x/../de`, `/team/%2e/de`. Accepted: `/DE`, `/de-at`, `/deutsch`, `/de/team`,
   `/team/de/..`, `/team/%64e`, a code only in the host. (`trailing_language` /
   `trailingLanguage`, vectors `vectors`.)

No startup error about `server.public_url` repeats the configured value: each names the key and
the reason only (the language rule also the code it found). A configuration file that is not
valid TOML is reported as `line L, column C: <reason>`, without the offending line.

### Texts and formatting

- Catalogue values are plain text. The shell generator HTML-escapes them; the pages insert them as
  text (`textContent`, Lit text bindings), never as HTML. A catalogue cannot put markup or script
  into a page.
- A placeholder in a template without a catalogue entry fails the build. So does a catalogue text
  placed inside a marker comment (the footer labels) that contains `--` or ends in `-`: it could
  end the comment early.
- At runtime there is no fallback to another language. Every catalogue has every key (a test
  enforces it); a key missing from the page's catalogue would show as the key itself. A page
  script running without a registered catalogue throws, naming the missing catalogue module.
- Plural texts use one key per `Intl.PluralRules` category of the language: `<key>#one`,
  `<key>#other`.
- Numbers, sizes (`1,5 KiB`), dates and the expiry (`Läuft in 2 Minuten ab`) are formatted with
  `Intl` in the **page** language, not the browser locale, so a page never mixes two languages.
- Error texts come from the catalogue by HTTP status and problem `code`; the English
  `problem.detail`/`title` of the API and the English messages of core are never shown. An unknown
  code gets a general text. Variants of an unreadable link collapse into "no key" and "key not
  readable".
- Legal pages in a shell of a language other than English carry `<article lang="en">`, so screen
  readers pronounce the English text correctly.

### What the build writes and what the server fills in

The web build does not know an instance's default language, so the generated shells leave two
things to the server as tokens:

- `%%capsulebin:prefix%%` in front of every internal link (`href="%%capsulebin:prefix%%/report"`,
  from the template placeholder `{{prefix}}`): replaced with nothing in the shells of the default
  language and with `/<lang>` in every other;
- `%%capsulebin:default%%` (from `{{default}}`): replaced with the configured default language.

The server replaces both in every shell it serves (`render` in `api/assets.rs`), with values fixed
at startup. The tokens pass through Vite unchanged; a shell never reaches a browser with one,
because `*.html` files are not served directly.

Nothing in a page depends on the request. With the embedded assets the server puts every page of
every language together once, when the routes are built — tokens, footer links and, for the legal
pages, title and text — and serves the prepared bytes from memory. With `server.asset_dir`
(directory mode, for development) it reads and fills the shell on every request, so an edited file
takes effect without a restart.

The assets are embedded at compile time in every build profile (`rust-embed` with `debug-embed`),
so a debug build without `server.asset_dir` serves the web build it was compiled with, like a
release build. A newer web build reaches such a server only through a new `cargo build` or
`cargo run`; `build.rs` makes Cargo recompile when `web/dist` has changed.

**Languages meta element**: every template has
`<meta name="capsulebin-languages" content="{{languages}}" data-default="{{default}}" />` in the
`<head>`, before the head scripts. The generator fills in every known language (core
`KNOWN_LANGUAGES`, space-separated), the server the default, so a served shell carries e.g.
`content="en de" data-default="en"`. `language-init.js` and the scripts (`defaultLanguage()`,
`offeredLanguages()`) read it; that is how the browser side learns which language is prefix-less.
Without the element the switch offers every known language, and the scripts take `en` as default.
`{{lang}}`, `{{languages}}`, `{{prefix}}` and `{{default}}` are the placeholders not taken from
the catalogue (catalogue keys always contain a dot).

**Server markers** (HTML comments, so a shell without substitution still renders):

- In every footer, one marker per legal page:
  `<!--capsulebin:legal-link:<page>:<label>-->` with `<page>` `imprint`, `privacy` or `terms`. The
  templates write `<!--capsulebin:legal-link:imprint:{{shell.imprint}}-->` and so on, so the shell
  generator fills in the label from the catalogue, HTML-escaped. The server replaces each marker
  with `<a href="<target>"><label></a>` when the page is configured (target with the language's
  prefix, or the configured `url`) and drops it otherwise; it holds no label text itself. A marker
  without its closing `-->` is left alone.
- `legal.html`: `<!--capsulebin:legal-title-->`, `<!--capsulebin:legal-content-->`, filled in after
  the tokens, so the operator's text is inserted as it is.

Tokens and markers are the same for every request, so a shell does not depend on the path id.

**Head order** in every shell: languages meta element, `<meta name="color-scheme">`,
`theme-init.js`, `language-init.js`, the catalogue module `register-<lang>.ts`, then the page
module. Both init scripts are external classic scripts without `defer`/`async`; the two modules
run in document order. `shells.test.ts` and `catalogue-modules.test.ts` check the order.

### Catalogue modules

There is one web build (`npm run build -w @capsulebin/web` is `vite build`) with every generated
shell of every language as input; the output is `dist/<lang>/<shell>.html` plus the shared
`dist/assets/`, which the server serves without a prefix whatever the default language (Vite
`base: '/'`).

Each language has a catalogue module `src/i18n/register-<lang>.ts` that imports `<lang>.json` and
passes it to `register()` in `language.ts`. The template line
`<script type="module" src="/src/i18n/register-{{lang}}.ts">` makes every shell load the module of
its own language before the page script. `language.ts` and the page scripts contain no catalogue
data: `t()`/`tn()` read whatever was registered. So the page scripts are the same files for every
language, and a page loads the texts of its own language only. The dev server and the unit tests
get their catalogue the same way (`tests/page-language.ts` registers the catalogue for a test).

The one exception is `src/i18n/language-next-page.ts`: the switch's notice in every language,
imported by `pages/shell.ts`, because it is shown in the chosen language. The catalogue files stay
the source (`shell.languageNextPage`); the texts are repeated there because a page script that
imported a catalogue file would pull the whole catalogue into a chunk every page loads.

`tests/catalogue-modules.test.ts` holds this in place: only `register-<lang>.ts` imports a
catalogue file, each its own; the shells load exactly the catalogue module and then the page
script; in the build output every page of a language reaches its own catalogue module and no
other; a language's texts appear in its catalogue module only; `LANGUAGE_NEXT_PAGE` equals the
catalogue entries and is the only text every page holds in every language.

### Dev server

`npm run dev -w @capsulebin/web` regenerates the shells when a template or catalogue changes and
answers the page routes like a server whose default language is `en`: English pages without a
prefix, German under `/de/`, tokens filled in per request. It does not redirect: paths under
`/en/…` and a bare `/en` or `/de` answer `404`, as does any unknown path. So does every path that
Vite would resolve to a raw template: a template's name with or without `.html` (`/index.html`,
`/p`, `/p.html`, `/manage`), under any directory (`/de/p.html`), in any letter case, also
percent-encoded or behind dot segments. The name decides, not the directory; only the generated
shells under `.shells/` keep these names.

### Adding a language

1. `src/server/web/src/i18n/<code>.json` with every key of `en.json`, including every plural
   category `Intl.PluralRules` has for the language.
2. `src/server/web/src/i18n/register-<code>.ts`, like the existing ones.
3. An entry for `<code>` in `LANGUAGE_NEXT_PAGE` (`src/i18n/language-next-page.ts`), equal to the
   catalogue's `shell.languageNextPage`.
4. `<code>` in `KNOWN_LANGUAGES` in `src/server/src/config/model.rs` and in
   `src/core/src/languages.ts`.

The shell generator picks up every catalogue file by itself. Every binary built with the language
offers it; operators cannot turn it off, but can make it the default. The new code is also refused
as the last path segment of a base URL from then on.

Tests fail when the lists drift apart: `src/server/tests/languages.rs` (server list vs. catalogue
files), `src/server/web/tests/i18n-catalogues.test.ts` (core list vs. catalogue files, same key
set, all plural forms, no empty value) and `tests/catalogue-modules.test.ts` (catalogue modules and
notice texts). `src/server/web/tests/shells.test.ts` fails on a visible text in a template that
does not come from the catalogue.

## Decisions

- **Language in the path, no cookie** — every page has a stable address per language; no cookie
  means nothing new is sent with requests and no `Vary` on pages. The choice lives in
  `localStorage` like the theme. See [ADR-016](adr/ADR-016-language-paths.md).
  (20261119-language-paths)
- **The default language has no prefix, and the server does not negotiate** — share and management
  links never carry a prefix and land directly on a page. Rejected: every language under a prefix,
  prefix-less paths redirected by `Accept-Language`; that needs a header parser, `Vary:
  Accept-Language` and a caveat for every cache in front, for a guess the head script makes better
  (it also knows the stored choice). (20261119-language-paths)
- **The default language's prefix redirects** (`302`, `no-store`) rather than serving a second copy
  — one address per page and language; `no-store` so a changed default takes effect at once. An
  unknown prefix is a `404`, not a redirect, to keep the set of page URLs small and unambiguous.
  (20261119-language-paths)
- **The operator chooses the default, not the offered languages** — a German instance keeps German
  prefix-less. A configurable list would cost validation, a languages marker filled in at runtime
  and legal footers per configured language; with every known language always offered the list is
  known at build time. (20261119-language-paths)
- **Shells generated at build time; one web build, one catalogue module per language** — no
  flicker, no extra request, CSP and reproducible build unchanged; every page loads only its own
  language and more languages make no page larger. Rejected: one bundle with every catalogue
  selected at runtime (every page ships every language); one Vite build per language (more
  machinery than the property needs). Removing the `register-<lang>` script from a template leaves
  the page without texts: the first `t()` throws. (20261119-language-paths)
- **Prefix and default as tokens the server fills in** — both depend on configuration the web build
  cannot know and are the same for every request, so a shell stays independent of the id.
  (20261119-language-paths)
- **Footer labels from the catalogue, targets from the server** — labels are interface text and
  follow the page language without per-language text in Rust; the server still decides per
  `[legal]` whether a link appears and where it points. (20261119-language-paths)
- **The "applies from the next page" notice in the chosen language** — whoever switches because
  they cannot read the page must be able to read the notice. It is the single deliberate exception
  to "only its own language", kept equal to the catalogues by a test. (20261119-language-paths)
- **`theme-init.js` first, then `language-init.js`, with a `color-scheme` meta** — the document
  `language-init.js` replaces is never styled; without the meta, narrowed to the stored theme by
  `theme-init.js`, the browser paints it in its light default canvas, a bright flash in dark mode.
  The meta needs no style, so it stays within the CSP. Both scripts duplicate their storage key on
  purpose (importing it would make them deferred modules); `language-init.test.ts` and
  `theme-init.test.ts` keep the copies equal. (20261119-language-paths)
- **The switch replaces the history entry** — a language change is no step to go back to, and an
  entry left behind would still hold the key in its fragment after the page has removed it from
  its own. (20261119-language-paths)
- **Store-only switch from the user's go-ahead, and no action on a page being left** — reloading
  after the key is removed from the address would lose it; reloading while a burn-after-reading
  retrieval or a deletion runs would consume the capsule on a page that never shows the outcome;
  reloading a create draft or a started report discards it (nothing of either is kept in the
  browser). Conversely, the old document stays usable until the new one arrives, so a confirmation
  in that gap must do nothing. The automatic retrieval has no click to hang the check on, hence the
  synchronous `beforeRetrieve` hook directly before the request. Removing the `isLeavingPage`
  checks or the hook brings back a retrieval (or burn) on a page that is being left and a second
  retrieval on the new page. (20261119-language-paths)
- **`parseLink` recognises the language segment** — users copy the link from the address bar after
  the browser moved to their language; without it the CLI would look for the API under
  `/de/api/…`. An unknown segment stays in `base` so a sub-path like `/cb` is not cut off.
  (20261119-language-paths)
- **Base URLs that a client could misread are refused, by one rule on both sides** — a base ending
  in a language code makes every link ambiguous; forbidding it keeps `parseLink` as it is. The rule
  works on the path as a URL parser normalizes it, because every client sees `/team/de/.` as
  `/team/de/`; CLI `put` checks too, because it takes its base from the user, not from the
  server's configuration. The server uses the `url` crate (already in the build through sqlx) so
  both sides normalize alike, and shared vectors fail the tests when they drift apart. A query or
  fragment is refused rather than repaired: with `…/team?x=/de` a request, creation token included,
  would go to `/team`. An unparseable value is an error, not "no language code", or it would pass
  every check unexamined. (20261119-language-paths)
- **Errors about `server.public_url` never repeat the value** — the rules refuse exactly what a
  share or management link pasted there by mistake looks like; quoting the value would put its
  paste id and link secret on stderr and into the service log. The same holds for TOML syntax
  errors, whose default rendering quotes the offending line. Adding "got …" back to these messages
  reopens the leak. (20261119-language-paths)
- **Pages of the embedded assets prepared once at startup; debug builds embed too** — everything a
  page contains is fixed at startup, so filling it per request was repeated work. Pages prepared
  at startup would name hashed script files that a later web build removes from disk, so every
  profile embeds the web build (`debug-embed`); reading from disk is what `server.asset_dir` is
  for. (20261119-language-paths)
- **The dev server answers `404` where it cannot serve like the real server** — otherwise Vite's
  HTML fallback serves a raw template with `{{lang}}` unfilled; Vite resolves a template from its
  name with or without `.html`, so the name decides. (20261119-language-paths)
- **Known languages listed three times** (server constant, core list, catalogue files) — server,
  core and web are built separately and none reads the others' files at runtime; tests keep them
  equal. (20261119-language-paths)

## Limits and open points

- **Legal texts are English in every language.** German legal texts, `[legal.<lang>.*]` and the
  matching amendment to ADR-015 are a follow-up.
- CLI messages and the API's `problem+json` `title`/`detail` are English. Core's
  `helpers/format.ts` stays English and platform-neutral; whether its `formatSize`/`formatExpiry`
  are removed is a separate clean-up.
- Operators cannot replace catalogues or choose which languages are offered; there is no third
  language yet.
- Changing `default_language` on a running instance moves pages: the old default's pages go under
  its prefix and the new default's prefixed addresses become redirects. Share and management
  links are unaffected (no prefix); a bookmarked page of the old default opens in the new one
  until the head script moves the browser to its language.
- The Vite dev server always runs with the default `en` and does not redirect `/en/…`; it answers
  those paths with `404`.
- Links issued by an earlier version under a base whose path ended in a language code are read by
  `parseLink` as carrying a language segment: CLI `get`/`delete` address the base without the
  code. Such an instance has to move to another base, see the upgrade note in
  [operations.md](operations.md#upgrades).
- Only `server.public_url` errors withhold the value; errors about other settings still repeat it.
- The access log redacts the language segment like any other unknown segment
  (`/{id}/p/{id}`).
- The German wording has not been reviewed by the project owner, and no text has had a legal
  review.
