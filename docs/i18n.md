# Interface languages

Every page of CapsuleBin exists once per interface language. The web interface is available in
English and German, and every instance offers both. The pages of the instance's default language
have no path prefix (`/p/{id}`); every other language lives under its prefix (`/de/p/{id}`). The
operator chooses only which language is the default (`[i18n] default_language`, `en` unless set).
Each language's shells are generated at build time from one set of templates and a catalogue per
language, and each shell loads the catalogue of its own language only: nothing is translated at
runtime, nothing is loaded afterwards and nothing flickers.
The server does not look at the browser's language. A head script in every shell moves the page
to the user's own choice, else to the browser language, else to the default. The CLI, the API's
`problem+json` texts and the legal texts stay English (see [Limits](#limits-and-open-points)).

## Rules

### Languages

Known languages: `en`, `de` (`KNOWN_LANGUAGES`, in this order). Codes are exact and lowercase.
Every known language is always offered; which ones are offered is not configurable.

The default language `D` is `[i18n] default_language` (env
`CAPSULEBIN__I18N__DEFAULT_LANGUAGE`), `en` unless set. It is the only key in `[i18n]`: a code
that is not a known language, or any other key in the table (`languages`, …), is a startup error
naming the key.

### Routes

`<prefix>` is empty for the default language `D` and `/L` for every other known language `L`:

| Path | Answer |
| --- | --- |
| `<prefix>/` | Create page (`index.html`) |
| `<prefix>/p/{id}` | View page (`p.html`) |
| `<prefix>/manage/{id}` | Management page (`manage.html`) |
| `<prefix>/report` | Report form (`report.html`) |
| `<prefix>/imprint`, `<prefix>/privacy`, `<prefix>/terms` | Legal page (`legal.html`) if it is served here, otherwise the generic `404` |
| `/L` (not the default) | `302` to `/L/`, query kept |
| `/D`, `/D/`, `/D/p/{id}`, … (every page path under the default language's prefix) | `302` to the same path without the prefix, query kept (`/D` → `/`) |

So with the default `en`, `/p/{id}` is the English page, `/de/p/{id}` the German one and
`/en/p/{id}` a redirect to `/p/{id}`; with `default_language = "de"` German is prefix-less,
English is under `/en/` and `/de/p/{id}` redirects.

Every shell answers `200`, `text/html; charset=utf-8`, `Cache-Control: no-store`, with
`<html lang>` of its language.

The redirects carry `Cache-Control: no-store` (a changed default language takes effect at once)
and an absolute path as `Location`. They copy the path without looking at it, so the answer does
not depend on whether an id exists and triggers no retrieval; the fragment with the key is never
sent and stays in the browser. The legal paths under `/D/` redirect even when the page is not
configured; the `404` then comes from the prefix-less path.

**The server does not negotiate.** `Accept-Language` changes no answer and no response carries
`Vary: Accept-Language`: a path alone decides which shell is served.

A prefix that is not a known language (`/fr/`, `/xx/p/{id}`, `/DE/`) gets the same generic `404`
as any unknown path. The API (`/api/…`), `/health/*` and static assets (`/assets/…`,
`/language-init.js`, `/theme-init.js`) have no prefix. A `*.html` path (`/de/index.html`) is never
served directly: shells only come through their route, with tokens and markers replaced.

### Choosing the language in the browser (`language-init.js`)

`public/language-init.js` runs in the `<head>` of every shell before anything is shown. The
language of the current path is its first segment if that is an offered language, otherwise the
default language. The script determines the wanted language in this order:

1. `localStorage` `capsulebin.language`, if that language is offered;
2. the first entry of `navigator.languages` whose primary subtag is offered;
3. the default language (`data-default` of the languages meta element).

If the result differs from the language of the path, it calls `location.replace` with the same
path in the wanted language — no prefix for the default language, `/<lang>` otherwise — plus
query and fragment, unchanged. Without the meta element, with a `data-default` that is not an
offered language, without `localStorage` or on any exception, it does nothing.

Examples on an instance with the default `en`: a German browser opening a share link
`/p/<id>#v1.…` lands on `/de/p/<id>#v1.…` and decrypts there; an English browser without a stored
choice following `/de/p/<id>#v1.…` lands on `/p/<id>#v1.…`, and stays on `/de/…` once German was
chosen in the switch.

### Language switch

In the header of every page, next to the theme toggle: one button per offered language, labelled
with its own name ("English", "Deutsch"), the page's language marked with `aria-current`, in the
order of the meta element. Hidden when only one language is offered (with today's two languages it
is always shown).

A choice stores `capsulebin.language` and loads the same path (query and fragment included) in
the chosen language — prefix-less for the default language — with `location.replace`, so the old
address does not stay behind as a history entry. Exception: once a page must not be reloaded any
more, the switch only stores the choice and says next to it that it applies from the next page
on. That point is

- on the view page: the user's go-ahead for the retrieval — the click that confirms the burn
  warning or submits the password. A capsule that needs neither is retrieved without a click;
  for it the point is the moment right before the retrieve request, after the key derivation
  (`OpenHooks.beforeRetrieve` in core, called with nothing asynchronous between it and the
  request). The same check runs there on the confirmed paths as well, where the switch is
  already store-only. In no case only when the key is later removed from the address;
- on the management page: when the deletion is confirmed;
- on the report form: the first input into any of its fields;
- on the create page: as soon as the form holds any user input — an item with content (text or a
  file) or a name the user typed, or any other field changed from its default (title, password,
  expiry, burn and the other options). It stays so if the form is emptied again, and on the page
  that shows the new links. On an untouched form the switch navigates.

Reloading at that point would lose the key from the fragment, run a burn-after-reading retrieval or
a deletion behind a page that never shows its outcome, or discard the draft or the started report
(nothing of either is kept in the browser). Once switched, it stays store-only for the rest of the
page.

The two orders exclude each other. A choice that navigates marks the page as being left: the old
document stays on screen until the new one arrives, so the switch disables every button and form
field in `<main>`, and the view and management pages refuse to start a retrieval or deletion from
it (`isLeavingPage`) — a burn confirmation, a password or a delete confirmation given in that gap
does nothing. The automatic retrieval of a capsule without burn warning and password asks the same
question right before its request: if the page is being left then, the old document sends no
`/retrieve` (`openPaste` ends with `aborted`), and the capsule is retrieved once, by the new page.
Whichever comes first wins: either the page is reloaded in the other language and
nothing was sent, or the action runs and the choice applies from the next page.

The notice appears in the **chosen** language, not the page's (and is marked with that `lang`):
someone who picks German because they cannot read the English page gets it in German. It is the
one text every page holds in every language, see [Catalogue modules](#catalogue-modules).

### Links

- Internal links in the shells and the pages (logo, "Create another", "Cancel", "Report content",
  the report link with `?id=` on the view page) point to the page's own language: no prefix on a
  page in the default language, `/L/…` otherwise.
- Footer links to legal pages served here follow the same rule (`/imprint`, `/de/imprint`); links
  in the built-in legal texts to the privacy notice and the report form too. Targets configured as
  `url` and links in the operator's Markdown stay as written.
- Share and management links created by the client have **no** prefix
  (`<origin>/p/<id>#v1.…`): they open in the default language, and the recipient's browser moves
  to its own language.
- `parseLink` in core drops a known language segment directly before `p`/`manage`
  (`https://x.example/de/p/<id>#…`) from `base`, so the CLI works with a link copied from the
  address bar. Any other segment, including an unknown two-letter one (`/cb/p/<id>`) or
  `de-AT`/`DE`, stays part of `base`.
- A `base` whose last segment is itself a language code cannot be told apart from a prefix
  (`https://example.org/team/de/p/<id>`): `parseLink` would drop the code and the capability would
  go to the shortened base. So no link is created below such a base, by one rule on both sides:
  the server refuses it as `server.public_url` (startup error naming the key, also from
  `capsulebin check`), and CLI `put` refuses it as `--server`/`CAPSULEBIN_SERVER` (usage error,
  exit code `2`, before anything is sent). `get` and `delete` take the base from the link and have
  no such check.
- The rule (`trailing_language` in the server, `trailingLanguage` in core): take the path as the
  WHATWG URL parser normalizes it — dot segments resolved, also percent-encoded ones (`%2e`), `\`
  read as `/` —, then its last non-empty segment, compared exactly with the known codes. Refused:
  `/de`, `/team/en`, `/team/de/`, `/team/de/.`, `/team/x/../de`, `/team/%2e/de`. Accepted: `/DE`,
  `/de-at`, `/deutsch`, `/de/team`, `/team/de/..`, `/team/%64e`, a code only in the host. It
  applies to every known code, whichever is the default. Both implementations are
  checked against the same vectors, `src/core/tests/fixtures/base-language.json`. That is the
  whole compatibility guarantee for links with a path in front of `p`/`manage`.
- A base with a query or a fragment is refused by both sides as well, before the language rule
  and whatever it contains (`…/team?lang=/de`, `…/team#/de`), also an empty one (`…/team?`,
  `…/team#`, `https://example.org?`): `server.public_url` is a startup error ("must not contain a
  query or fragment", also from `capsulebin check`), CLI `put` answers `--server`/
  `CAPSULEBIN_SERVER` with a usage error (exit code `2`, nothing sent). Request paths and links
  are appended to the base as text and would end up inside the query or fragment. The check runs
  on the base as given, before a trailing slash is removed (`…/team?x=1/`). A percent-encoded
  `%3F` or `%23` is path and accepted. The rule (`has_query_or_fragment` in the server,
  `hasQueryOrFragment` in core) has its vectors under `query_or_fragment` in the same fixture.
- The rule needs a parsed URL, so text that no URL parser accepts is refused as well: a
  `server.public_url` with an http(s) prefix that the `url` crate cannot parse
  (`https://exa mple.org/team/de`, `https://`, `http://example.org:port`) is a startup error
  ("not a valid URL"), and CLI `put` answers such a `--server` with the usage error "must be an
  http(s) URL".
- No startup error about `server.public_url` repeats the configured value: each names the key and
  the reason only (the language rule also the code it found). A configuration file that is not
  valid TOML is reported as `line L, column C: <reason>`, without the offending line.

### Texts and formatting

- Catalogue values are plain text. The shell generator HTML-escapes them; the pages insert them as
  text (`textContent`, Lit text bindings), never as HTML. A catalogue cannot put markup or script
  into a page.
- A placeholder in a template without a catalogue entry fails the build. So does a catalogue text
  placed inside a marker comment (the footer labels) that contains `--` or ends in `-`: it could
  end the comment early.
- At runtime there is no fallback to another language. Every catalogue has every key (a test
  enforces it); a key missing from the page's catalogue would show as the key itself. A page
  script running without a registered catalogue throws, naming the missing catalogue module.
- Plural texts use one key per `Intl.PluralRules` category of the language: `<key>#one`,
  `<key>#other`.
- Numbers, sizes (`1,5 KiB`), dates and the expiry (`Läuft in 2 Minuten ab`) are formatted with
  `Intl` in the **page** language, not the browser locale, so a page never mixes two languages.
- Error texts come from the catalogue by HTTP status and problem `code`; the English
  `problem.detail`/`title` of the API and the English messages of core are never shown. An unknown
  code gets a general text. Variants of an unreadable link collapse into "no key" and "key not
  readable".

### What the build writes and what the server fills in

The web build does not know an instance's default language, so the generated shells leave two
things to the server as tokens:

- `%%capsulebin:prefix%%` in front of every internal link (`href="%%capsulebin:prefix%%/report"`,
  from the template placeholder `{{prefix}}`): replaced with nothing in the shells of the default
  language and with `/<lang>` in every other;
- `%%capsulebin:default%%` (from `{{default}}`): replaced with the configured default language.

The server replaces both in every shell it serves (`render` in `api/assets.rs`), with values fixed
at startup. The tokens pass through Vite unchanged; a shell never reaches a browser with one,
because `*.html` files are not served directly.

Nothing in a page depends on the request. With the embedded assets the server therefore puts every
page of every language together once, when the routes are built — tokens, footer links and, for
the legal pages, title and text — and serves the prepared bytes from memory. With
`server.asset_dir` (directory mode, for development) it reads and fills the shell on every request,
so an edited file takes effect without a restart.

The assets are embedded at compile time in every build profile (`rust-embed` with `debug-embed`),
so a debug build without `server.asset_dir` serves the web build it was compiled with, like a
release build. A newer web build reaches such a server only through a new `cargo build` or
`cargo run`; `build.rs` makes Cargo recompile when `web/dist` has changed.

**Languages meta element**: every template has
`<meta name="capsulebin-languages" content="{{languages}}" data-default="{{default}}" />` in the
`<head>`, before `language-init.js`. The generator fills in every known language (core
`KNOWN_LANGUAGES`, space-separated), the server the default, so a served shell carries e.g.
`content="en de" data-default="en"`. `language-init.js` and the scripts (`defaultLanguage()`,
`offeredLanguages()`) read it; that is how the browser side learns which language is prefix-less.
Without the element the switch offers every known language, and the scripts take `en` as default.
`{{lang}}`, `{{languages}}`, `{{prefix}}` and `{{default}}` are the placeholders not taken from
the catalogue (catalogue keys always contain a dot).

**Server markers** (HTML comments, so a shell without substitution still renders):

- In every footer, one marker per legal page:
  `<!--capsulebin:legal-link:<page>:<label>-->` with `<page>` `imprint`, `privacy` or `terms`. The
  templates write `<!--capsulebin:legal-link:imprint:{{shell.imprint}}-->` and so on, so the shell
  generator fills in the label from the catalogue, HTML-escaped (no `>`, and the build rejects a
  label with `--` or a trailing `-`, so a label cannot end the comment). The server replaces each
  marker with `<a href="<target>"><label></a>` when the page is configured (target with the
  language's prefix, or the configured `url`) and drops it otherwise; it holds no label text
  itself. A marker without its closing `-->` is left alone.
- `legal.html`: `<!--capsulebin:legal-title-->`, `<!--capsulebin:legal-content-->`, filled in after
  the tokens, so the operator's text is inserted as it is.

Tokens and markers are the same for every request, so a shell still does not depend on the path
id.

**Script order** in every shell: languages meta element, `language-init.js`, `theme-init.js`, the
catalogue module `register-<lang>.ts`, then the page module. Both init scripts are external
classic scripts without `defer`/`async`; the two modules run in document order.

### Catalogue modules

There is one web build (`npm run build -w @capsulebin/web` is `vite build`) with every generated
shell of every language as input; the output is `dist/<lang>/<shell>.html` plus the shared
`dist/assets/`, which the server serves without a prefix.

Each language has a catalogue module `src/i18n/register-<lang>.ts` that imports `<lang>.json` and
passes it to `register()` in `language.ts`. The template line
`<script type="module" src="/src/i18n/register-{{lang}}.ts">` makes every shell load the module of
its own language before the page script. `language.ts` and the page scripts contain no catalogue
data: `t()`/`tn()` read whatever was registered. So the page scripts are the same files for every
language, and a page loads the texts of its own language only. The dev server and the unit tests
get their catalogue the same way (`tests/page-language.ts` registers the catalogue for a test).

The one exception is `src/i18n/language-next-page.ts`: the switch's notice in every language,
imported by `pages/shell.ts`, because it is shown in the chosen language. The catalogue files stay
the source (`shell.languageNextPage`); the texts are repeated there because a page script that
imported a catalogue file would pull the whole catalogue into a chunk every page loads.

`tests/catalogue-modules.test.ts` holds this in place: only `register-<lang>.ts` imports a
catalogue file, each its own; the shells load exactly the catalogue module and then the page
script; in the build output every page of a language reaches its own catalogue module and no
other; a language's texts appear in its catalogue module only; `LANGUAGE_NEXT_PAGE` equals the
catalogue entries and is the only text every page holds in every language.

### Dev server

`npm run dev -w @capsulebin/web` regenerates the shells when a template or catalogue changes and
answers the page routes like a server whose default language is `en`: English pages without a
prefix, German under `/de/`, tokens filled in per request. It does not redirect: paths under
`/en/…` and a bare `/en` or `/de` answer `404`, as does any unknown path. So does every path that
Vite would resolve to a raw template: a template's name with or without `.html` (`/index.html`,
`/p`, `/p.html`, `/manage`), under any directory (`/de/p.html`), in any letter case, also
percent-encoded or behind dot segments. The name decides, not the directory; only the generated
shells under `.shells/` keep these names.

### Adding a language

1. `src/server/web/src/i18n/<code>.json` with every key of `en.json`, including every plural
   category `Intl.PluralRules` has for the language.
2. `src/server/web/src/i18n/register-<code>.ts`, like the existing ones.
3. An entry for `<code>` in `LANGUAGE_NEXT_PAGE` (`src/i18n/language-next-page.ts`), equal to the
   catalogue's `shell.languageNextPage`.
4. `<code>` in `KNOWN_LANGUAGES` in `src/server/src/config/model.rs` and in
   `src/core/src/languages.ts`.

The shell generator picks up every catalogue file by itself. Every binary built with the language
offers it; operators cannot turn it off, but can make it the default.

The language switch names it by `Intl.DisplayNames` in its own language. Tests fail when the lists
drift apart: `src/server/tests/languages.rs` (server list vs. catalogue files),
`src/server/web/tests/i18n-catalogues.test.ts` (core list vs. catalogue files, same key set, all
plural forms, no empty value) and `tests/catalogue-modules.test.ts` (catalogue modules and notice
texts, see above). `src/server/web/tests/shells.test.ts` fails on a visible text in a template
that does not come from the catalogue.

## Decisions

- **Language in the path, not in a cookie or only in the browser** — every page has a stable
  address per language. No cookie, so nothing new is sent with requests; the choice lives in
  `localStorage` like the theme. See [ADR-016](adr/ADR-016-language-paths.md).
  (20261119-language-paths)
- **The default language has no prefix** — shorter URLs, and share and management links, which
  never carry a prefix, land directly on a page instead of on a redirect. Rejected: every language
  under a prefix, with prefix-less paths redirected by `Accept-Language`; that needs a header
  parser in the server, `Vary: Accept-Language` on the redirect and a caveat for every cache in
  front of it, for a guess the head script corrects anyway. (20261119-language-paths)
- **No `Accept-Language` negotiation in the server** — the browser language is applied by
  `language-init.js`, which also knows the stored choice. The server's answers depend on the path
  alone. (20261119-language-paths)
- **The prefix of the default language redirects** (`302`, `no-store`) instead of serving a second
  copy or a `404` — one address per page and language; `no-store` so that a changed default
  language takes effect at once. `Location` is an absolute path without `public_url`.
  (20261119-language-paths)
- **The operator chooses the default language, not the offered languages** — a German instance
  keeps German prefix-less. Rejected: a configurable language list; it would cost validation, a
  languages marker filled in at runtime and legal footers per configured language, for little
  value. With every known language always offered the list is known at build time.
  (20261119-language-paths)
- **Prefix and default as tokens the server fills in** — both depend on configuration the web
  build cannot know, and they are the same for every request, so the shell stays independent of
  the id. The language list in the meta element needs no server: the generator writes it from
  core's `KNOWN_LANGUAGES`. (20261119-language-paths)
- **Shells generated at build time, not translated at runtime** — no flicker, no extra request, CSP
  and reproducible build unchanged. (20261119-language-paths)
- **One web build, one catalogue module per language, loaded by the shell** — every page loads
  only its own language, more languages make no page larger, and the page scripts are shared.
  Rejected: one bundle with every catalogue, selected by `<html lang>` at runtime (every page
  ships every language); one Vite build per language with a build-time catalogue and a check of
  the output (more machinery than the property needs). Removing the `register-<lang>` script from
  a template leaves the page without texts: the first `t()` throws. (20261119-language-paths)
- **The "applies from the next page" notice in the chosen language, held in every language by
  every page** — whoever switches because they cannot read the page must be able to read the
  notice. It is the single deliberate exception to "only its own language", kept equal to the
  catalogues by a test. (20261119-language-paths)
- **`language-init.js` before `theme-init.js`** — after a redirect the theme no longer matters.
  The storage key is duplicated in the script on purpose (importing it would make it a deferred
  module); `language-init.test.ts` keeps both equal. (20261119-language-paths)
- **Store-only switch from the start of a retrieval or deletion, not only once the key is gone** —
  reloading after `history.replaceState` would lose the fragment; reloading while a
  burn-after-reading retrieval or a deletion is under way would consume the capsule on a page that
  never shows it. (20261119-language-paths)
- **Store-only switch on the create page once any field holds input** — a reload in the other
  language would discard the draft, and a title, password or expiry already set is a draft too. It
  does not switch back when the form is emptied, so the behaviour does not flip while typing.
  (20261119-language-paths)
- **The switch replaces the history entry** (`location.replace`) — a language change is no step to
  go back to, and an entry left behind would still hold the key in its fragment after the page has
  removed it from its own. (20261119-language-paths)
- **`server.public_url` must not end in a language code** — a link like
  `https://example.org/team/de/p/<id>` would be ambiguous between a sub-path ending in `de` and the
  `/de/` prefix. Forbidding such a base URL keeps every link unambiguous; `parseLink` stays as it
  is. Comparison is exact, like `parseLink`'s, and applies to every known code whichever is the
  default. (20261119-language-paths)
- **One rule for server and clients, on the path as a URL parser normalizes it, with shared
  vectors** — a link built on `/team/de/.` reaches every client as `/team/de/…`, so a check on the
  configured text alone would let such a base through; and CLI `put` takes its base from the
  user, not from the server's configuration, so without its own check it would hand out links
  that `get` and `delete` then address to the shortened base. The server uses the `url` crate
  (already in the build through sqlx) rather than its own string handling so that both sides
  normalize alike; the fixture fails the tests when they drift apart. (20261119-language-paths)
- **An unparseable `server.public_url` is a startup error, not "no language code"** — the scheme
  prefix alone lets text through that no client can use as a URL; if the language check treated
  it as harmless, `https://exa mple.org/team/de` would pass every check unexamined.
  (20261119-language-paths)
- **Errors about `server.public_url` name key and reason, never the value** — the rules above
  refuse exactly what a share or management link pasted there by mistake looks like (a fragment,
  a path); an error quoting the value would put its paste id and link secret on stderr and into
  the service log. For the same reason a TOML syntax error gives position and reason instead of
  the parser's own rendering, which quotes the offending line (a link written without quotes).
  Adding "got …" back to these messages for convenience reopens the leak.
  (20261119-language-paths)
- **The language switch and opening, burning or deleting exclude each other from the first
  click** — after a navigating choice the old document stays usable until the new one arrives; a
  confirmation given in that gap would burn or delete the capsule on a page that never shows the
  outcome. The other way round, the switch becomes store-only at the user's go-ahead, not only at
  the request that follows the key derivation, which leaves no gap either. Removing the
  `isLeavingPage` checks or moving `languageFromNextPage` back to the request reopens the race.
  (20261119-language-paths)
- **The automatic retrieval decides right before the request, through a hook in core** — a
  capsule without burn warning and password has no click to hang the check on, and its retrieval
  did not ask `isLeavingPage` at all: after a navigating choice the old document still sent its
  `/retrieve`, the capsule was retrieved (or burned) on a page that never showed it, and the new
  page retrieved it again. `OpenHooks.beforeRetrieve` is synchronous and called directly before
  the request, after the key derivation, so nothing can slip in between check and request; it is
  also the point from which the switch is store-only on this path, no longer the start of the
  derivation. Removing the hook or its `startOpening` check brings the second retrieval back.
  (20261119-language-paths)
- **A base URL with a query or fragment is refused, an empty one included** — the API client and
  the link builder append paths to the base as text. With `https://example.org/team?x=/de` the
  request, together with a creation token, would go to `/team`, and the language rule saw nothing
  wrong because the path does not end in a code. Refusing on the text (`?` or `#` anywhere)
  rather than repairing it keeps one simple rule on both sides. (20261119-language-paths)
- **Store-only switch on the report form from the first input** — the same principle as the create
  draft: a reload would discard the started report, and no report data is stored in the browser to
  bring it back. (20261119-language-paths)
- **Pages of the embedded assets prepared once at startup** — tokens, footer links and legal texts
  are fixed at startup and the embedded assets cannot change while the server runs, so filling the
  shell on every `GET` was repeated work. The directory mode keeps reading per request because
  its files are meant to change under a running server. The path id is no input either way.
  (20261119-language-paths)
- **Debug builds embed the web build too** (`debug-embed`) — without the feature a debug build
  reads `web/dist` from disk on every access. The pages are put together once at startup, so after
  a web build under a running server they would name scripts (hashed file names) that are gone
  from the directory. With it every profile serves pages and scripts from one build; reading from
  disk remains what `server.asset_dir` is for. (20261119-language-paths)
- **Footer labels from the catalogue, targets from the server** — the labels are interface text and
  must follow the page language; written by the shell generator, they need no per-language text in
  Rust. The server still decides, per `[legal]`, whether a link appears and where it points.
  Rejected: the server writing English labels into one footer marker. (20261119-language-paths)
- **A prefix that is not a known language is a `404`, not a redirect** — keeps the set of page URLs
  small and unambiguous. (20261119-language-paths)
- **The dev server answers `404` for paths it cannot serve as the real server does** — without it,
  Vite's HTML fallback would serve the raw template with `{{lang}}` unfilled; it resolves a
  template from its name with or without `.html`, so the dev server decides by the name.
  (20261119-language-paths)
- **`Intl` follows the page language** — otherwise text and number/date formats mix.
  (20261119-language-paths)
- **Known languages listed three times** (server constant, core list, catalogue files) — server,
  core and web are built separately and none reads the others' files at runtime. Tests keep them
  equal; adding a language is therefore more than "just a catalogue".
  (20261119-language-paths)
- **`parseLink` recognises the language segment** — users copy the link from the address bar after
  the browser moved to their language; without it the CLI would look for the API under
  `/de/api/…`. An unknown segment stays in `base` so a sub-path like `/cb` is not cut off.
  (20261119-language-paths)
- **`dist/<lang>/<shell>.html`, assets stay under `/assets/`** (Vite `base: '/'`) — the server needs
  no prefix for assets, whatever the default language. (20261119-language-paths)
- **Catalogue values are plain text** — escaped by the generator, inserted as text by the pages.
  (20261119-language-paths)
- **No `*.html` through the static fallback** — a shell served that way would lack the token and
  marker replacement. (20261119-language-paths)
- **Legal paths under the default language's prefix always redirect** — the redirect then depends
  only on the path. (20261119-language-paths)
- **`<article lang="en">` on legal pages in a non-English shell** — screen readers pronounce the
  English text correctly until translated legal texts exist. (20261119-language-paths)
- **`src/core/src/helpers/format.ts` stays unchanged** — the web client has its own localised
  formatting; core stays platform-neutral and English. Whether core's `formatSize`/`formatExpiry`
  are removed is a separate clean-up. (20261119-language-paths)
- **Pages show catalogue texts by status/code, never `problem.detail`** — the API's texts are
  English and stay so. (20261119-language-paths)

## Limits and open points

- **Legal texts are English in every language.** German legal texts, `[legal.<lang>.*]` and the
  matching amendment to ADR-015 are a follow-up package.
- CLI messages and the API's `problem+json` `title`/`detail` stay English. The CLI prints links
  without a prefix.
- Operators cannot replace catalogues or choose which languages are offered; there is no third
  language yet.
- Changing `default_language` on a running instance moves pages: the old default's pages go under
  its prefix and the new default's prefixed addresses become redirects. Share and management
  links are unaffected (no prefix); a bookmarked page of the old default opens in the new one
  until the head script moves the browser to its language.
- The Vite dev server always runs with the default `en` and does not redirect `/en/…`; it answers
  those paths with `404`.
- Links issued by an instance whose base path ended in a language code (possible before this
  rule) are read by `parseLink` as carrying a language segment: CLI `get`/`delete` address the
  base without the code. Such an instance has to move to another base, see the upgrade note
  in [operations.md](operations.md#upgrades).
- The access log redacts the language segment like any other unknown segment
  (`/{id}/p/{id}`).
- The German wording was not approved by the project owner as part of the change, and the texts
  have had no legal review.
