# Interface languages

Every page of CapsuleBin exists once per interface language, under a path prefix
(`/en/p/{id}`, `/de/p/{id}`). The web interface is available in English and German; every
instance offers every language the binary was built with, English being the default. Each
language's shells are generated at build time from one set of templates and a catalogue per
language, and the web client is built once per language, so every page carries only its own
language's texts: nothing is translated at runtime, nothing is loaded afterwards and nothing
flickers.
Links without a prefix, above all share and management links, are redirected by the server
according to `Accept-Language`. In the browser, the order is: the user's own choice, then the
browser language, then English. The CLI, the API's `problem+json` texts and the
legal texts stay English (see [Limits](#limits-and-open-points)).

## Rules

### Languages

Known languages: `en`, `de` (`KNOWN_LANGUAGES`, in this order). Codes are exact and lowercase.
Every known language is offered; there is no configuration for it. The default language is `en`
(`DEFAULT_LANGUAGE` in the server, `src/server/web/src/default-language.ts` in the web client).

### Routes

For each known language `L`:

| Path | Answer |
| --- | --- |
| `/L/` | Create page (`index.html`) |
| `/L/p/{id}` | View page (`p.html`) |
| `/L/manage/{id}` | Management page (`manage.html`) |
| `/L/report` | Report form (`report.html`) |
| `/L/imprint`, `/L/privacy`, `/L/terms` | Legal page (`legal.html`) if it is served here, otherwise the generic `404` |
| `/L` | `302` to `/L/`, query kept |

Every shell answers `200`, `text/html; charset=utf-8`, `Cache-Control: no-store`, with
`<html lang="L">`.

The prefix-less page paths `/`, `/p/{id}`, `/manage/{id}`, `/report`, `/imprint`, `/privacy`,
`/terms` answer `302` with `Location: /<lang><path>` and the query kept
(`/report?id=X` → `/de/report?id=X`), plus `Vary: Accept-Language` and `Cache-Control: no-store`.
The legal paths redirect even when the page is not configured; the `404` then comes under the
prefix.

A prefix that is not a known language (`/fr/`, `/xx/p/{id}`, `/DE/`) gets the same
generic `404` as any unknown path. The API (`/api/…`), `/health/*` and static assets
(`/assets/…`, `/language-init.js`, `/theme-init.js`) have no prefix. A `*.html` path
(`/en/index.html`) is never served directly: shells only come through their route, with the
markers replaced.

### Choosing the language of a redirect (server)

Among the known languages, the one with the highest `q` in `Accept-Language` wins:

- Several `Accept-Language` field lines count as one comma-separated list (RFC 9110).
- Matching uses the primary subtag, case-insensitively (`de-AT` → `de`).
- `q=0` rules a language out; on equal weight the earlier entry wins.
- Entries are parsed strictly: a language range (`1*8ALPHA *("-" 1*8alphanum)`, so `de-`,
  `de--AT`, `de_AT` are not ranges), optionally followed by exactly one `;q=<qvalue>` (`q`
  case-insensitive, blanks allowed around `;`, none around `=`). Any other or further parameter
  (`de;level=1`, `de;q=1;q=1`, `de;q = 0.7`), a malformed entry and `*` are skipped.
- A header with a line that is not valid text, or whose lines together are longer than 1024 bytes,
  is ignored as a whole.
- No match or no header: `en`.

The redirect copies the path without looking at it, so its answer does not depend on whether an id
exists, and it triggers no retrieval. The fragment with the key is never sent and stays in the
browser across the redirect.

### Choosing the language in the browser (`language-init.js`)

`public/language-init.js` runs in the `<head>` of every shell before anything is shown. It
determines the language in this order:

1. `localStorage` `capsulebin.language`, if that language is offered;
2. the first entry of `navigator.languages` whose primary subtag is offered;
3. `data-default` of the languages meta element (`en`).

If the result differs from the current prefix, it calls
`location.replace('/<lang>' + <rest of the path> + search + hash)`; the fragment goes along
unchanged. Without the meta element, without `localStorage`, on a path without an offered prefix
or on any exception, it does nothing.

So the server's `Accept-Language` choice is only a first guess: a stored choice overrides it on
the next page, and a browser whose language list puts a different offered language first is moved
there. An English browser following a `/de/p/…` link lands on `/en/p/…` unless German was chosen.

### Language switch

In the header of every page, next to the theme toggle: one button per offered language, labelled
with its own name ("English", "Deutsch"), the page's language marked with `aria-current`, in the
order of the meta element. Hidden when only one language is offered (with today's two languages it
is always shown).

A choice stores `capsulebin.language` and loads the same path (query and fragment included) under
the new prefix with `location.replace`, so the old address does not stay behind as a history
entry. Exception: once a page must not be reloaded any more, the switch only stores the choice and
says next to it that it applies from the next page on. That point is

- on the view page: when the retrieval starts (after a burn confirmation and the password, right
  before the retrieve request), not only when the key is later removed from the address;
- on the management page: when the deletion is confirmed;
- on the create page: as soon as any item holds content — text, a file, or a name the user typed.
  It stays so if the form is emptied again, and on the page that shows the new links. On an empty
  form the switch navigates.

Reloading at that point would lose the key from the fragment, run a burn-after-reading retrieval or
a deletion behind a page that never shows its outcome, or discard the draft. Once switched, it stays
store-only for the rest of the page.

### Links

- Internal links in the shells and the pages (logo, "Create another", "Cancel", "Report content",
  the report link with `?id=` on the view page) carry the prefix of the current page.
- Footer links to legal pages served here carry the shell's prefix (`/de/imprint`); links in the
  built-in legal texts to the privacy notice and the report form too. Targets configured as `url`
  and links in the operator's Markdown stay as written.
- Share and management links created by the client have **no** prefix
  (`<origin>/p/<id>#v1.…`): the recipient's language is decided on their side.
- `parseLink` in core drops a known language segment directly before `p`/`manage`
  (`https://x.example/de/p/<id>#…`) from `base`, so the CLI works with a link copied from the
  address bar. Any other segment, including an unknown two-letter one (`/cb/p/<id>`) or
  `de-AT`/`DE`, stays part of `base`. A `base` whose last segment is itself a language code cannot
  be told apart from a prefix (`https://example.org/team/de/p/<id>`), so `server.public_url` must
  not end in one: a path whose last non-empty segment is exactly a known code (`/de`, `/team/en`,
  `/de/`) is a startup error naming the key; `/DE`, `/de-at`, `/deutsch` or `/de/team` are
  accepted, matching `parseLink`. That is the whole compatibility guarantee for links with a path
  in front of `p`/`manage`.

### Texts and formatting

- Catalogue values are plain text. The shell generator HTML-escapes them; the pages insert them as
  text (`textContent`, Lit text bindings), never as HTML. A catalogue cannot put markup or script
  into a page.
- A placeholder in a template without a catalogue entry fails the build, and so does a key the
  scripts name that a catalogue lacks (in any plural form of the language). At runtime there is
  no fallback to another language; a key missing from the page's catalogue would show as the key
  itself, which the build rules out.
- Plural texts use one key per `Intl.PluralRules` category of the language: `<key>#one`,
  `<key>#other`.
- Numbers, sizes (`1,5 KiB`), dates and the expiry (`Läuft in 2 Minuten ab`) are formatted with
  `Intl` in the **page** language, not the browser locale, so a page never mixes two languages.
- Error texts come from the catalogue by HTTP status and problem `code`; the English
  `problem.detail`/`title` of the API and the English messages of core are never shown. An unknown
  code gets a general text. Variants of an unreadable link collapse into "no key" and "key not
  readable".

## Structure

| Where | What |
| --- | --- |
| `src/server/src/config/model.rs` | `KNOWN_LANGUAGES`, `DEFAULT_LANGUAGE` (`capsulebin_server::config::…`); rejects a `public_url` ending in a language code |
| `src/server/src/config.rs` | `Resolved.legal` (each known language with its rendered legal pages) |
| `src/server/src/api/assets.rs` | Routes per prefix, redirect and `Accept-Language` negotiation, legal marker replacement, `LegalByLanguage` (legal pages per language, `AppState.legal`), `has_shells` for `/health/ready` |
| `src/server/src/legal.rs`, `legal/defaults.rs` | Legal pages and footer link targets (`FooterLinks`) per language (prefix in the links, `lang="en"` on the article) |
| `src/server/web/{index,p,manage,report,legal}.html` | Shell templates with `{{lang}}`, `{{languages}}`, `{{default}}` and `{{<key>}}` placeholders |
| `src/server/web/src/i18n/<lang>.json` | Catalogues, flat `key → text`, including the footer labels `shell.imprint`, `shell.privacy`, `shell.terms` |
| `src/server/web/scripts/shells.ts` | Generator: one shell per template and catalogue into `.shells/<lang>/` (git-ignored), including the languages meta element |
| `src/server/web/src/default-language.ts` | `DEFAULT_LANGUAGE` of the web client: `data-default` of the meta element, fallback of `pageLanguage()` |
| `src/server/web/scripts/catalogue.ts` | `virtual:catalogue`: the texts the scripts use, for one language (production) or every language chosen by `<html lang>` (dev server, unit tests) |
| `src/server/web/scripts/build.ts` | `npm run build`: generates the shells, runs one Vite build per catalogue language into the shared `dist/`, then checks the output |
| `src/server/web/scripts/check-dist.ts` | Checks the build output (see [Build](#build-one-web-build-per-language)) |
| `src/server/web/vite.config.ts` | Moves the generated shells to `dist/<lang>/<shell>.html`, splits language-free code into its own chunks; in the dev server serves `/en/…`, `/de/…` with every catalogue and answers `404` for prefix-less page paths, a bare `/en` and the raw templates (`appType: 'mpa'`, no SPA fallback) |
| `src/server/web/public/language-init.js` | Head script, see above |
| `src/server/web/src/language.ts` | `pageLanguage()`, `t()`, `tn()`, `formatSize`, `formatExpiry`, `formatDateTime`, `formatNumber`, `localPath()`, switch logic |
| `src/server/web/src/pages/shell.ts` | `mountLanguageSwitch`, `languageFromNextPage` (store-only mode, idempotent); called by `view.ts`, `manage.ts`, `create.ts` |
| `src/server/web/src/pages/errors.ts` | Error texts by status and code for the pages; `report.ts` maps the report endpoint's codes |
| `src/core/src/languages.ts` | `KNOWN_LANGUAGES`, `isKnownLanguage` |
| `src/core/src/links.ts` | `parseLink` with the language segment |

**Languages meta element**, written by the shell generator: every template has
`<meta name="capsulebin-languages" content="{{languages}}" data-default="{{default}}" />` in the
`<head>`, before `language-init.js`; the generator fills in every known language (core
`KNOWN_LANGUAGES`, space-separated) and `DEFAULT_LANGUAGE`, so every shell carries
`content="en de" data-default="en"`. `language-init.js` and the switch read it. Without it the
switch offers every known language. `{{lang}}`, `{{languages}}` and `{{default}}` are the
placeholders not taken from the catalogue (catalogue keys always contain a dot).

**Server markers** (HTML comments, so the shells still render unmodified in the Vite dev server):

- In every footer, one marker per legal page:
  `<!--capsulebin:legal-link:<page>:<label>-->` with `<page>` `imprint`, `privacy` or `terms`. The
  templates write `<!--capsulebin:legal-link:imprint:{{shell.imprint}}-->` and so on, so the shell
  generator fills in the label from the catalogue, HTML-escaped (no `>`, so a label cannot end the
  comment). The server replaces each marker with `<a href="<target>"><label></a>` when the page is
  configured (target with the language prefix, or the configured `url`) and drops it otherwise; it
  holds no label text itself. A marker without its closing `-->` is left alone.
- `legal.html`: `<!--capsulebin:legal-title-->`, `<!--capsulebin:legal-content-->`.

The markers are the same for every request, so a shell still does not depend on the path id.

**Head script order** in every shell: languages meta element, `language-init.js`, `theme-init.js`,
then the page module. Both init scripts are external classic scripts without `defer`/`async`.

### Build: one web build per language

`npm run build -w @capsulebin/web` runs `scripts/build.ts`, not Vite directly:

1. It empties `dist/` and generates the shells (`.shells/<lang>/<shell>.html`) for every catalogue
   file in `src/i18n/`.
2. For each of those languages it runs one Vite build with that language's five shells as input
   and that language's catalogue as `virtual:catalogue`. Every build writes `dist/<lang>/*.html`
   and adds its chunks to the shared `dist/assets/`.
3. It checks the output (`scripts/check-dist.ts`) and fails on any finding.

`src/language.ts` imports its texts from `virtual:catalogue` (`scripts/catalogue.ts`). That module
holds only the texts the scripts use: every string literal in `src/**/*.ts` that is a catalogue
key, a plural key with every `Intl.PluralRules` category of the language. Texts only the shell
templates use stay in the HTML. In the Vite dev server and the unit tests (`vitest.config.ts`)
the module instead holds every language and answers for `<html lang>` on each lookup, so `/en/…`
and `/de/…` share one module graph and tests can switch the page language.

Chunk names carry a content hash. `vite.config.ts` puts `node_modules` and `@capsulebin/core` into
chunks of their own (`vendor`, split by the pages that use them; DOMPurify as `dompurify`), so
code that does not depend on the language comes out byte-identical in every build and exists once
under `/assets/`; only the chunks that import the catalogue differ per language. The server still
serves every asset under `/assets/` without a prefix.

The output check fails if

- a JS file reachable from `dist/<lang>/*.html` contains, as a whole string, a text of another
  language that differs from its own for the same key, is not one of its own texts and is longer
  than 3 characters (a short allowlist covers library strings that equal a catalogue text, e.g.
  highlight.js's "Plain text");
- any JS asset names a key that only the shell templates use;
- the chunks without texts (and without imports of chunks with texts, followed transitively and
  safe against import cycles) are not the same files for every language, or two of them have the
  same content.

"Reachable" follows every quoted path ending in `.js` (`src=`, `href=`, `from`, `import()`) whose
file name exists in `dist/assets/`. The pattern deliberately allows any characters but quotes and
whitespace: Rollup puts whatever it likes into chunk names (`vendor~p~manage-….js`), and a narrower
pattern silently skips such chunks, so their texts are never checked.

### Adding a language

1. `src/server/web/src/i18n/<code>.json` with every key of `en.json`, including every plural
   category `Intl.PluralRules` has for the language. The web build picks up every catalogue file
   by itself: one more set of shells and one more Vite build, no list in the web client to extend.
2. `<code>` in `KNOWN_LANGUAGES` in `src/server/src/config/model.rs` and in
   `src/core/src/languages.ts`.

Every binary built with it offers it; operators cannot turn it off.

The language switch names it by `Intl.DisplayNames` in its own language; nothing else needs the
code. Tests fail when the three lists drift apart: `src/server/tests/languages.rs` (server list vs.
catalogue files) and `src/server/web/tests/i18n-catalogues.test.ts` (core list vs. catalogue files,
same key set, all plural forms, no empty value). `src/server/web/tests/shells.test.ts` fails on a
visible text in a template that does not come from the catalogue; the build fails if the new
catalogue lacks a text the scripts use or if a text of it leaks into another language's scripts.

## Decisions

- **Language in the path, not in a cookie or only in the browser** — every page has a stable
  address per language, and the server can redirect prefix-less links. No cookie, so nothing new
  is sent with requests; the choice lives in `localStorage` like the theme. See
  [ADR-016](adr/ADR-016-language-paths.md). (20261119-language-paths)
- **Shells generated at build time, not translated at runtime** — no flicker, no extra request, CSP
  and reproducible build unchanged. (20261119-language-paths)
- **Catalogues resolved at build time, one web build per language** — like the shells: every page
  ships only its own language, and more languages do not make any page larger. Rejected: one
  shared bundle with every catalogue, selected by `<html lang>` at runtime — every page would ship
  every language and grow with each new one. The price is one Vite build per language;
  language-free code is split into its own chunks so it still exists once.
  (20261119-language-paths)
- **Scripts get only the keys they name** — found by scanning `src/**/*.ts` for string literals that
  are catalogue keys. This works because keys are always written out whole (`TextKey`/`PluralKey`
  are literal types); building a key from parts (`` `error.${code}` ``) would escape the scan, and
  the build would then not carry that text. A literal that merely looks like a key costs one text.
  (20261119-language-paths)
- **DOMPurify in a named chunk** — splitting libraries into vendor chunks moved it out of the
  Markdown renderer; the browser tests allow Chromium's CSP report of its inert parse by the chunk
  name `dompurify`. Renaming or merging that chunk breaks the hostile-Markdown browser test.
  (20261119-language-paths)
- **Dev server and unit tests keep every catalogue** — one Vite dev server serves both prefixes from
  one module graph, and tests switch `<html lang>`; only the production build is per language.
  (20261119-language-paths)
- **Every known language is always offered, `en` is the default; no configuration for it** —
  Rejected: letting the operator choose the offered languages and the default. That would cost
  configuration, startup validation, a languages marker the server fills into every shell at
  runtime and legal footers per configured language, for little value. With a fixed set the
  language list is known at build time and the shells need nothing from the server for it.
  (20261119-language-paths)
- **A prefix that is not a known language is a `404`, not a redirect** — keeps the set of page URLs
  small and unambiguous. (20261119-language-paths)
- **`302` with `Vary: Accept-Language` and `no-store`** — the answer depends on a request header and
  must not be cached or shared by a cache. `Location` is an absolute path without `public_url`,
  like the existing links. (20261119-language-paths)
- **Languages and default as a `<meta>` written by the shell generator** — the shell stays
  independent of the id and of the request, and the head script reads it synchronously. The values
  come from core's `KNOWN_LANGUAGES` and the web client's `DEFAULT_LANGUAGE`, so the server inserts
  nothing for it. The default exists
  twice (server constant, web constant) because server and web are built separately.
  (20261119-language-paths)
- **`language-init.js` before `theme-init.js`** — after a redirect the theme no longer matters.
  The storage key is duplicated in the script on purpose (importing it would make it a deferred
  module); `language-init.test.ts` keeps both equal. (20261119-language-paths)
- **Store-only switch from the start of a retrieval or deletion, not only once the key is gone** —
  reloading after `history.replaceState` would lose the fragment; reloading while a
  burn-after-reading retrieval or a deletion is under way would consume the capsule on a page that
  never shows it. (20261119-language-paths)
- **Store-only switch on the create page once it holds content** — a reload under the other prefix
  discarded the draft. It does not switch back when the form is emptied, so the behaviour does not
  flip while typing. (20261119-language-paths)
- **The switch replaces the history entry** (`location.replace`) — a language change is no step to
  go back to, and an entry left behind would still hold the key in its fragment after the page has
  removed it from its own. (20261119-language-paths)
- **Strict `Accept-Language` parsing, field lines combined** — follows RFC 9110; a lenient parser
  read `de;q=0; q=1` or `de-` as German. A malformed entry is skipped, never an error.
  (20261119-language-paths)
- **`server.public_url` must not end in a language code** — a link like
  `https://example.org/team/de/p/<id>` would be ambiguous between a sub-path ending in `de` and the
  `/de/` prefix. Forbidding such a base URL keeps every link unambiguous; `parseLink` stays as it
  is. Comparison is exact, like `parseLink`'s. (20261119-language-paths)
- **Footer labels from the catalogue, targets from the server** — the labels are interface text and
  must follow the page language; written by the shell generator, they need no per-language text in
  Rust. The server still decides, per `[legal]`, whether a link appears and where it points.
  Rejected: the server writing English labels into one footer marker. (20261119-language-paths)
- **The dev server answers `404` for paths it cannot serve as the real server does** — without it,
  Vite's SPA fallback served the raw template with `{{lang}}` unfilled. (20261119-language-paths)
- **`Intl` follows the page language** — otherwise text and number/date formats mix.
  (20261119-language-paths)
- **Known languages listed three times** (server constant, core list, catalogue files) — server,
  core and web are built separately and none reads the others' files at runtime. Tests keep them
  equal; adding a language is therefore a catalogue file plus two code lists, not "just a
  catalogue". (20261119-language-paths)
- **`parseLink` recognises the language segment** — users copy the link from the address bar after
  the redirect; without it the CLI would look for the API under `/de/api/…`. An unknown segment
  stays in `base` so a sub-path like `/cb` is not cut off. (20261119-language-paths)
- **`dist/<lang>/<shell>.html`, assets stay under `/assets/`** (Vite `base: '/'`) — the server needs
  no prefix for assets; content-hashed names keep the per-language chunks apart and the shared ones
  single. (20261119-language-paths)
- **Catalogue values are plain text** — escaped by the generator, inserted as text by the pages.
  (20261119-language-paths)
- **No `*.html` through the static fallback** — a shell served that way would lack the marker
  replacement. (20261119-language-paths)
- **Prefix-less legal paths always redirect** — the redirect then depends only on the path.
  (20261119-language-paths)
- **`<article lang="en">` on legal pages in a non-English shell** — screen readers pronounce the
  English text correctly until translated legal texts exist. (20261119-language-paths)
- **`src/core/src/helpers/format.ts` stays unchanged** — the web client has its own localised
  formatting; core stays platform-neutral and English. Whether core's `formatSize`/`formatExpiry`
  are removed is a separate clean-up. (20261119-language-paths)
- **Pages show catalogue texts by status/code, never `problem.detail`** — the API's texts are
  English and stay so. (20261119-language-paths)

## Limits and open points

- **Legal texts are English under every prefix.** German legal texts, `[legal.<lang>.*]` and the
  matching amendment to ADR-015 are a follow-up package.
- CLI messages and the API's `problem+json` `title`/`detail` stay English. The CLI prints links
  without a prefix.
- Operators cannot replace catalogues or choose which languages are offered; there is no third
  language yet.
- The Vite dev server does not redirect prefix-less paths, it answers them with `404`: open `/en/…`
  or `/de/…` directly. Its shells carry the languages meta element, so the head script and the
  switch work as in production.
- The access log redacts the language segment like any other unknown segment
  (`/{id}/p/{id}`).
- The German wording was not approved by the project owner as part of the change, and the texts
  have had no legal review.
