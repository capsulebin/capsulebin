# Threat model

What CapsuleBin protects, against whom, how — and what it explicitly does not. The binding
decisions behind it are [ADR-001](adr/ADR-001-trust-model.md) (zero knowledge) and
[ADR-013](adr/ADR-013-abuse-reports-and-moderation.md) (abuse handling); the cryptography is
specified in [crypto-profile.md](crypto-profile.md).

## Assets

| Asset | Where it lives | Who may know it |
| --- | --- | --- |
| Plaintext (content, file names, media types, item count, title) | Only in the creating and the receiving client | Creator and recipients |
| Link secret | URL fragment of the share link (`#v1.…`) | Creator and recipients |
| Password | The creator's and recipients' heads | Creator and recipients |
| Content key | Derived in the client, never stored | Nobody beyond the clients |
| Reveal token | Derived in the client, sent on retrieval | Clients; the server sees it once per retrieval and stores only `SHA-256` |
| Delete secret | Fragment of the management link | Creator only |
| Creation token | Operator, configured as a domain-separated hash | Operator and the people it is issued to |
| Ciphertext, public header, verifiers | SQLite database, backups | Server and operator — useless without the link secret |
| Lifecycle metadata (size, timestamps, burn flag) | SQLite database | Server and operator |
| Abuse reports (description, optional contact) | SQLite database, backups | Operator — personal data |
| Client IP addresses | Rate-limiter memory only, never persisted | Server process |

## Trust boundary

The server is trusted to **store, enforce limits and serve the application** — not with content.
Everything left of the boundary sees plaintext; everything right of it must not.

```
 creator client ─┐                          ┌──────────── server ─────────────┐
                 │  ciphertext, header,     │ Axum: limits, capabilities,     │
                 ├─ verifiers ─────────────▶│ lifecycle, assets               │
 recipient ──────┤                          │ SQLite: ciphertext + metadata   │
                 │◀─ ciphertext on proof ───│ operator CLI: backup, moderation│
                 │   of the reveal token    └─────────────────────────────────┘
   plaintext, keys, link secret, password never cross this line
```

## Adversaries and controls

| Adversary / threat | Controls | Verified by | Residual risk |
| --- | --- | --- | --- |
| **Database or backup leak** | AES-256-GCM ciphertext; no keys, secrets or content metadata stored; verifiers only (`SHA-256`, domain-separated); backups compacted so freed pages of deleted pastes are not copied | `db_no_plaintext.rs` (CI gate), backup tests, `smoke.sh` greps DB and backup for secrets | Padded sizes (order of magnitude), timestamps and lifecycle flags are visible. Reports contain personal data. |
| **Curious or compelled operator** | Same as above; operator tools work on ids and metadata only, never decrypt | — (by construction) | Operator sees who creates when (via logs on the proxy, not in CapsuleBin), and sizes. |
| **Malicious or compromised server shipping modified JavaScript** | Embedded assets, strict CSP, no third-party resources; the CLI as a client that does not depend on served code; reproducible web assets, so a tag's client can be rebuilt and compared with what a server ships | CSP asserted on every response (`smoke.sh`); two web builds compared byte for byte (`scripts/reproducible-web.sh`, CI) | **Not prevented.** A compromised server can exfiltrate keys from web users. This is the model's documented limit (ADR-001). |
| **Network observer** | HTTPS (at the reverse proxy, with HSTS); the fragment is never sent; `Referrer-Policy: no-referrer`; ciphertext padded (PADMÉ) | Security headers in `smoke.sh`, padding tests and golden vectors | Server IP, timing and padded sizes are observable. |
| **Link preview bots and scanners** | A share link `GET /p/{id}` (and `/{lang}/p/{id}` in every other language) serves the same static shell for every id; a path under the default language's prefix answers a `302` to the path without it, copied without inspecting the id; the server never reads `Accept-Language`; nothing looks the id up, retrieval is an explicit `POST` with the reveal token | `view_shell_is_identical_for_every_id`, `the_prefix_of_the_default_language_is_redirected_away`, `smoke.sh` | Scanners that execute JavaScript and hold the full link (fragment included) can consume a burn capsule. |
| **Someone who learns a paste id** (logs, history, proxy, report form) | Descriptor, retrieval and delete each need a capability derived from the link (describe token, reveal token, delete secret); ids are 128-bit random; ids are redacted from the access log | `the_descriptor_needs_a_capability`, `logging.rs` (CI gate), property test on `redact_path` | None: without the link the id answers like an unknown one. |
| **Existence probing** (does id X exist?) | Every endpoint taking an id requires a capability; unknown, expired, consumed, disabled, deleted and wrong-capability answer identically; the check runs against a dummy verifier for unknown ids; reports are answered identically whether or not the id exists or a report ceiling was reached | `the_descriptor_needs_a_capability`, `wrong_token_and_unknown_id_are_indistinguishable`, `moderated_pastes_look_exactly_like_unknown_ones`, report tests incl. `dropped_reports_answer_like_stored_ones`, `smoke.sh` | Small timing differences (e.g. a stored vs. an unstored report); mitigated by rate limits and the id space. |
| **Brute force of ids, reveal tokens or delete secrets** | 128-/256-bit randomness; failed attempts are optionally throttled per client before any lookup | `tests/rate_limits.rs`, `smoke.sh` over a real socket | None practical at these key sizes. |
| **Online password guessing** (link leaked, password not) | Every guess needs a retrieve with a reveal token derived from it; retrieves of one paste that prove the link but fail the reveal token are limited from any address (`invalid_capability_per_paste`, on by default), checked and charged atomically so parallel guesses cannot exceed the burst; keyed on the id the retrieve handler looked the paste up by, so every spelling of the id in the URI (percent-encoded in upper- or lower-case hex, fully or partly) shares one budget | `tests/rate_limits.rs`, `parallel_password_guesses_cannot_exceed_the_per_paste_burst`, `password_attempts_share_one_budget_across_id_spellings`, `password_attempts_across_id_spellings_are_limited_under_concurrency` | Roughly 14 000 guesses a day per capsule at the default; weak passwords still fall eventually. |
| **Blocking a capsule by its id** (id leaked, link not) | The per-paste limit counts only retrieves that prove the link with the describe token, and is checked only after that proof; describe and delete never touch it; this holds for every spelling of the id | `a_caller_with_only_the_id_cannot_block_a_capsule`, `a_caller_with_only_the_id_cannot_drain_the_budget_in_any_spelling`, `password_attempts_on_one_paste_are_limited_by_default_from_any_address` | A link holder can keep the password limit drained - but could retrieve or burn the capsule anyway. |
| **Offline password guessing** | The link secret is a mandatory second factor; PBKDF2 (600 000 iterations by default, versioned, never fewer than 100 000 accepted); no password verifier in the public header; ciphertext only after a correct reveal token | Golden vectors, `public_header` tests | Someone who has the link **and** the ciphertext can guess offline. Weak passwords fall. |
| **A link issuer guessing the recipient's password offline** (a hostile link names its own server and KDF parameters; the reveal token derived from the password goes to that server) | Clients refuse a public header with fewer than 100 000 PBKDF2 iterations, a non-integer count or a password salt other than 16 bytes, before a password is asked for or a reveal token derived (web and CLI share the parser; reported as an invalid capsule). The CLI uses `CAPSULEBIN_PASSWORD` only for links to the server named with `get --server`/`CAPSULEBIN_SERVER` (scheme, host, port and path compared); for any other link it stops non-interactively or prompts | `public_header.test.ts`, `properties.test.ts`, `public_header` vectors in `golden-vectors.test.ts`, `open.test.ts` (no password hook, no retrieve), `cli.test.ts` (origin match and mismatch, exit codes `5` and `8`) | A password typed into the prompt or given with `--password-file` is sent (as a reveal token) to whatever server the link names; at 100 000 iterations a weak password still falls to an issuer who guesses offline. |
| **Capabilities over cleartext or redirected transport** (a CLI pointed at `http://`, a proxy or attacker answering with a redirect) | The CLI refuses plain `http://` for `put --server` and the link of `get`/`delete` except on `localhost`, `127.0.0.0/8` and `[::1]`, unless `--allow-http`/`CAPSULEBIN_ALLOW_HTTP=1`; the core API client (web and CLI) follows no redirect on any API request and does not show the `Location`; `put` does not retry a refused redirect | `redirect.test.ts` (two real servers: the redirect target receives nothing), `cli.test.ts` (HTTP policy, redirect exit code `7` with one create request) | `--allow-http` sends capabilities unencrypted, by the user's choice. Names under `.localhost` and private networks need the opt-in like any host. |
| **Links exposed on the creator's or recipient's machine** (argv visible in `ps`, shell history, logs that capture stderr or JSON) | `get`/`delete` read the link from stdin (`-`) or `--link-file`; `put --delete-link-file` writes the management link to a new owner-only (`0600`) file, created exclusively before the upload, and then leaves it out of stderr and the JSON output; error messages never quote what was read | `cli.test.ts` (round trips, usage errors without input, file mode, existing file refused, file removed on failure), `smoke.sh` (no `#v1.` on stderr of `put`/`get`/`delete`, mode `600`) | A link given as an argument still works and is still exposed; the share link is still printed on stdout. |
| **XSS through Markdown or code** | Only Markdown renders HTML: marked → DOMPurify allowlist → link policy; highlight.js escapes; strict CSP; Trusted Types required; no inline scripts or styles | `xss.test.ts`, `trusted-html-usage.test.ts`, CSP in `smoke.sh`; browser tests (`src/server/web/e2e`) in Chromium, Firefox and WebKit with hostile Markdown, an XSS canary and every CSP/Trusted Types violation failing the test | Sanitizer or browser bugs. |
| **Script through the operator's legal texts** (`[legal]`, ADR-015) | The operator is trusted, but the text lands on every visitor's screen: rendered at startup without raw HTML or images, links limited to http(s), mailto, tel and local paths, `url` values to absolute http(s) URLs and single-slash paths; strict CSP on the pages | `legal/markdown.rs` tests (raw HTML, unsafe links, images, escaping), `legal/tests.rs` (URL allowlist), `legal.e2e.ts` under the CSP guard | A misleading but harmless text; the operator controls the instance anyway. |
| **Malicious capsule** (crafted by a creator to attack the recipient's client) | AES-GCM authenticates the whole container; strict, length-checked parser that never allocates from unchecked sizes; files are only downloaded, never previewed. CLI `get`: item content is only ever written to files, never to stdout, so it never reaches a terminal as output; every diagnostic on stderr (manifest text in errors, file and directory names) escapes all control characters, newlines included, and `--json` writes DEL and C1 as `\u00NN`; file names keep only the last path component and lose C0, DEL and C1; every file is created exclusively (`wx`) with mode `0600`, so an existing entry at the name — file, directory, symlink, dangling or not — is never opened, followed or replaced: the item takes the next free name; new directories are `0700`; a failed write removes the files and the multi-item directory this run created | Property tests on the decoder (arbitrary, corrupted, truncated input); `escape.test.ts` (every code point and byte in U+0000–U+00FF, random strings); `cli.test.ts` (`file output`: modes under umask `000`, existing files, symlinks and directories at the name, no free name, failed write, the multi-item directory, `--here`/`-o`, empty stdout; `terminal output`: escaped server problems, `created`/`wrote` lines, JSON bytes) | Downloaded files are as dangerous as any download; opening a written file (`cat` included) passes its bytes on unchanged. Bidi and invisible characters (U+202A–U+202E, U+2066–U+2069, zero-width) are not escaped in diagnostics and can still make text read differently than it is. A process killed during a write can leave a partial owner-only file under the item's name. File modes are not asserted on Windows. |
| **A malicious server's messages** (problem `title`/`code` crafted to forge terminal output or extra `capsulebin:` lines) | The CLI escapes every control character of server text on stderr, newlines included, whether or not stderr is a terminal; `--json` writes DEL and C1 as `\u00NN`; the last-resort message in `main.ts` goes through the same function | `cli.test.ts` (`terminal output`: 4xx and 5xx with ESC, newline and U+009B in title and code; JSON error bytes), `escape.test.ts` | Printable text from the server is shown as it is. |
| **A hostile or broken server exhausting a client** (a link to an instance that answers with an endless or huge body, never answers, or stalls mid-body; a capsule padded beyond the format) | In the core API client (web and CLI) oversized responses are cut off: every body, error bodies included, is read as a stream and counted whatever `Content-Length` says, at most 64 KiB, a successful retrieve at most the base64url of the largest valid ciphertext (`MAX_CAPSULE_BYTES` + 16) plus 1 KiB; above that the stream is cancelled (`response_too_large`). Each request has a total deadline (30 s for describe and delete, 10 min for create and retrieve), and a body that delivers no bytes for 30 s is cancelled (`timeout`); both are status `0` like a network error, so the web client shows its network error text and the CLI exits `7`. `openPaste` refuses a ciphertext above `MAX_CAPSULE_BYTES` + 16 before decrypting, and the capsule decoder refuses input above `MAX_CAPSULE_BYTES` before scanning it. `put` retries a timeout with the same sealed paste, never an oversized response | `limits.test.ts` (`oversized responses are cut off` for every endpoint and error statuses, without, with a wrong and with a correct `Content-Length`; `a capsule at the size limit still opens`; `requests time out` with fake timers), `limits.acceptance.test.ts` (an error body of exactly 64 KiB read, one byte more cut off; a create not cut off at 30 s; a stalled describe or error body times out), `capsule.test.ts`, `open.test.ts` (no decrypt call), `errors.test.ts` (web text), `cli.test.ts` (exit `7`, reasons, retry counts) | A client still holds up to about 13.4 MiB of a retrieve answer in memory, and a server can keep a recipient waiting up to 10 minutes. A burn capsule whose retrieve times out after the server answered is consumed without being shown. The report page's own requests (same origin only) are not bounded this way. |
| **A local input too large for a capsule** (`put` given a huge file, a pipe that never ends or a special file like `/dev/zero`) | `put` sums the sizes of the regular input files and refuses a sum above `MAX_CAPSULE_BYTES` before reading any; then it reads all inputs, stdin included, within one budget of `MAX_CAPSULE_BYTES` and stops at the first byte beyond it. Exit code `2`, a message naming the limit in bytes, nothing sent | `cli.test.ts` (`put refuses inputs above the capsule limit before reading them`, `put stops reading at the capsule limit`: endless stdin, `/dev/zero`, file plus stdin) | — |
| **A terminal left broken or a guarded request sent anyway** (Ctrl-C or EOF at a CLI prompt) | Prompts use a real output stream; readline restores echo and line mode on an answer, Ctrl-C and EOF; Ctrl-C (`interrupted`) and EOF (`input_closed`) end with exit code `8` before the create or retrieve the prompt guards | `terminal.test.ts` on a python3 pseudo-terminal against the bundled CLI: hidden password (typed marker never shown), burn confirmation `y`/`n`/Ctrl-C/EOF, Ctrl-C and EOF at the password prompt of `get`, Ctrl-C at the first one of `put`, request counts at the fake API, `stty -a` after every run | A process killed with `SIGKILL` at a prompt cannot restore the terminal. |
| **Burn races** (two recipients, or a scanner and a recipient) | `BEGIN IMMEDIATE` burn transaction with an affected-row check; rate-limited and unauthorized requests never reach it | Repository and HTTP-level race tests, 20-connection race in `smoke.sh` | "Burned" means first *authorized retrieval*, not "read by a human". |
| **I/O amplification by unauthorized requests** | Descriptor, retrieve and delete check capabilities against metadata only; the payload is read after authorization | `metadata_lookups_do_not_read_the_payload` | — |
| **Storage and resource abuse** | Token creation mode by default; create decides the creation capability from the request head (mode, `Authorization`) before a body byte is read, and a disabled report endpoint answers `404 reports_disabled` unread; body and plaintext limits: create up to `max_body_bytes`, describe, retrieve and delete 4 KiB, reports 32 KiB, each `413 payload_too_large` for a declared and a streamed body; per-client request rates, daily byte quota, concurrent-upload cap; retention purge; open reports (`open` or `reviewing`) capped per capsule (`abuse.max_open_reports_per_paste`, default 10) and per instance (`abuse.max_open_reports`, default 1000), checked and inserted in one statement, a report above a ceiling dropped with the same `202` | `tests/rate_limits.rs`, `api.rs` size tests, `an_unauthorized_create_never_reads_the_body`, `a_streamed_create_above_the_body_limit_is_refused`, `proof_routes_have_a_small_body_limit` (`api.rs`); `disabled_reports_never_read_the_body`, `reports_have_a_small_body_limit`, `dropped_reports_answer_like_stored_ones` (`abuse.rs`); `open_reports_are_capped_per_paste_and_globally`, `the_report_ceiling_holds_under_concurrency` (abuse repository); `reports_list_starts_with_the_open_reports_and_both_ceilings`, `a_report_ceiling_below_one_stops_the_binary` (`report_ceilings_acceptance.rs`, on the binary) | Public-mode instances remain abusable within the limits. Unauthorized creates still pass the byte quota and concurrency checks before they are refused. No server-side body timeout and no instance-wide upload budget: slow or many parallel bodies are left to the reverse proxy. Reports about one capsule, or junk about many, can fill the ceilings and crowd out later genuine reports until an operator closes them. |
| **Illegal content** | Notice and action: report by id, operator disables or deletes without decrypting; audit trail | `tests/abuse.rs`, `smoke.sh` | No preventive moderation under zero knowledge. |
| **A key pasted into a report** (a reporter copies the whole share or management link into the description or contact) | The report page sends only the id from the id field (the fragment is cut off first) and refuses a description or contact containing `#v1.` before any request exists: no `POST`, a message in the page language, focus on the first field concerned, the text left for the reporter to correct. The detection rule is one core function (`containsKeyFragment` in `src/core/src/links.ts`), exactly the server's rule; the server refuses such text too, for other clients | `containsKeyFragment` tests (`src/core/tests/links.test.ts`), `report-page.test.ts` (no `POST`, message, focus, text kept), `the report form refuses a link with its key in the description or contact` (`capsule.e2e.ts`, requests counted in the browser), `a_report_containing_a_key_is_refused` and `accepted_reports_carry_no_key_and_no_control_characters` (server) | A bare key without `#` (`v1.…` or the base64url secret alone) is not detected, in the browser or on the server. A client other than the report page sends the text before the server refuses it. |
| **A password that protects nothing** (the creator types only whitespace) | The create page refuses a non-empty password made only of whitespace before anything is encrypted or sent, with a message below the password field; an empty field means no password, and spaces around real characters stay part of the password. CLI `put` refuses one from `--password-file` or `CAPSULEBIN_PASSWORD` (exit code `2`, naming the source, not the value) before any request; the core `Paste` refuses it for every client before sealing, while `''` and `null` mean no password | `create-page.test.ts` (no request, message, focus, inputs kept; `' secret '` opens only with the spaces), `a password of only spaces is refused before anything is sent` (`capsule.e2e.ts`), `paste.test.ts`, `cli.test.ts` (no request; `' secret '` from a file opens only with the spaces) | `get` does not refuse a whitespace-only password; it simply fails to open the capsule. |
| **Rate-limit evasion via spoofed `X-Forwarded-For`** | Header honoured only when the TCP peer is in `trusted_proxies`; right-most untrusted address is used | `tests/rate_limits.rs` | Misconfigured `trusted_proxies` (too broad) re-opens it. |
| **Secrets in logs** | Access log records method and redacted path only; no bodies, no `Authorization`; report text never logged; a report dropped at a ceiling leaves one warning a minute at most, without the paste id, text or contact; `Debug` impls redact. Configuration errors on stderr (and from there the service log) name `server.public_url` and the reason, never its value — a share or management link pasted there by mistake carries the paste id and the link secret; a file that is not valid TOML is reported by line, column and reason without quoting the line (the same link written without quotes). `server.public_url` with user information, whitespace or control characters is refused at startup, so credentials never reach share links or problem type URIs | `logging.rs` (CI gate); `public_url_errors_never_repeat_the_value`, `public_url_with_credentials_whitespace_or_controls_is_refused`, `toml_syntax_errors_do_not_quote_the_file` (`config/tests.rs`), `ac25_check_never_repeats_a_rejected_public_url`, `ac25_serve_does_not_start_with_a_rejected_public_url` (`check` and `serve` on the binary, value from the file and from the environment) | Logs of the reverse proxy are outside CapsuleBin's control — configure them not to log query strings or bodies. Only `server.public_url` is protected this way: errors about other settings (e.g. `i18n.default_language`, a `[legal]` `url`) still repeat the rejected value, so a secret pasted into the wrong key can reach the log. |
| **Crafted database files** (restore of an untrusted backup) | `restore` copies only the backup's main file into a private stage directory and runs verification (integrity, schema, not newer) and migration on that standalone copy, never on the input path, so a `-wal` next to the backup never reaches SQLite | `restore_ignores_a_valid_sibling_wal`, `restore_migrates_a_private_copy_before_the_cutover` (`backup/tests.rs`) | The bundled SQLite treats the main file as trusted input (RUSTSEC-2026-0459, exception in `deny.toml` until SQLx allows a fixed SQLite): restore only your own backups. |
| **A restore that fails halfway** (disk full, a migration error, a failed rename, the process killed) | The copy is verified, migrated and checkpointed before anything outside the stage moves; the old database and its `-wal`/`-shm` move to `<file>.pre-restore-<now>` only at the cutover, and any failure undoes every move made so far and removes the stage. A missing database next to `<file>.pre-restore-*` or a `.<file>.restore-*` directory stops every command that opens the database instead of creating an empty one | `restore_failure_at_every_step_keeps_the_old_database`, `restore_refuses_an_existing_aside_name`, `restore_recovers_next_to_an_old_aside`, `dry_run_migrates_a_private_copy_and_changes_nothing` (`backup/tests.rs`); `missing_database_with_restore_leftovers_is_not_recreated` (`database_files_acceptance.rs`); `dry_run_reports_the_migrated_version_and_changes_nothing`, `forced_restore_keeps_the_old_database_with_its_sidecars` (`restore_acceptance.rs`, real binary) | A restore killed during the cutover is detected (the server refuses to start), not repaired: the operator restores again or moves the old database back. Stage directories left by a killed run stay until the operator removes them. If moving back fails too, the error lists what to move by hand. |
| **Other local users on the host** (reading the database, its `-wal`/`-shm` or a backup; planting a symlink under a scratch name an operator command writes to) | A missing database is created by CapsuleBin exclusively with mode `0600` whatever the umask (SQLite gives `-wal`/`-shm` the same mode); backups are written `0600` inside a new `0700` stage directory and renamed to the output name only if no entry exists there (checked before the snapshot and right before the rename; `rename` follows no symlink); the write probe and the restore stage use random names created exclusively; `serve` and `check` warn about database files with group/other permissions and a database directory others can write | `new_database_files_are_private`, `permissive_database_files_are_reported`, `write_probe_follows_no_planted_entry` (`database_files_acceptance.rs`, real binary under umask `022`); `backup_stages_privately_and_cleans_up_on_failure`, `backup_never_replaces_or_follows_an_existing_entry`, `restore_follows_no_planted_scratch_entry` (`backup/tests.rs`) | Existing files keep their modes: permissive ones are only reported. A user who can write the database directory can still replace files there, including an entry created between `restore`'s last collision check and its `rename`s, which replace it (accepted: the server is stopped, and such a user could replace the database anyway). Likewise, an entry created in a backup's output directory between `backup`'s last check and its `rename` is replaced (accepted: only a user who can write that directory could do it, and such a user could replace the backup anyway). Modes are enforced on Unix only. |
| **Supply chain** | Lockfiles, `cargo deny`, `npm audit`, minimal dependencies, `unsafe_code = "forbid"`; base images pinned by digest; actions pinned to commit SHAs; releases with an SBOM, `SHA256SUMS` and keyless cosign signatures | `cargo deny check`, `npm audit`, Grype scan of the container image (fixable high/critical fail), each also weekly | Advisories without a fix (currently a dev-only `picomatch` ReDoS); vulnerabilities in the base image without a fixed Debian package are reported, not blocked. |

## Explicit non-goals

- Protection against a fully compromised server for **web** users (see above).
- Physical erasure. SQLite's `secure_delete` overwrites burned, deleted and purged ciphertext with
  zeros in the database file, and the write-ahead log is truncated after checkpoints
  (`secure_delete.rs`). Beyond that file nothing is promised: WAL frames until the next checkpoint,
  the filesystem, SSD wear levelling and older backups may still hold ciphertext.
- Anonymity: CapsuleBin does not hide who talks to the server.
- Preventive content scanning, proof of reading, or recovery of lost links.

## Keeping this current

A change that adds a data path, an endpoint, a log line or a stored field updates the table above
and adds the test that backs the new row.
