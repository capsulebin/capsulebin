# Threat model

What CapsuleBin protects, against whom, how — and what it explicitly does not. The binding
decisions behind it are [ADR-001](adr/ADR-001-trust-model.md) (zero knowledge) and
[ADR-013](adr/ADR-013-abuse-reports-and-moderation.md) (abuse handling); the cryptography is
specified in [crypto-profile.md](crypto-profile.md).

## Assets

| Asset | Where it lives | Who may know it |
| --- | --- | --- |
| Plaintext (content, file names, media types, item count, title) | Only in the creating and the receiving client | Creator and recipients |
| Link secret | URL fragment of the share link (`#v1.…`) | Creator and recipients |
| Password | The creator's and recipients' heads | Creator and recipients |
| Content key | Derived in the client, never stored | Nobody beyond the clients |
| Reveal token | Derived in the client, sent on retrieval | Clients; the server sees it once per retrieval and stores only `SHA-256` |
| Delete secret | Fragment of the management link | Creator only |
| Creation token | Operator, as a domain-separated hash in the configuration or in the database (`creation_tokens`, ADR-019); issued to clients (CLI, a browser's `localStorage` `capsulebin.creation_token`, the fragment of an invitation link `#token=…`) | Operator and the people it is issued to |
| Ciphertext, public header, verifiers | SQLite database, backups | Server and operator — useless without the link secret |
| Lifecycle metadata (size, timestamps, burn flag) | SQLite database | Server and operator |
| Retired ids (the id of every purged capsule, nothing else) | SQLite database (`retired_ids`), backups; kept forever | Server and operator |
| Creation token records (hash, operator label, creation and revocation time, day of last use; no link to any capsule) | SQLite database (`creation_tokens`), backups; revoked ones kept forever | Operator — a label may name a person |
| Abuse reports (description, optional contact) | SQLite database, backups | Operator — personal data |
| Client IP addresses | Rate-limiter memory only, never persisted | Server process |

## Trust boundary

The server is trusted to **store, enforce limits and serve the application** — not with content.
Everything left of the boundary sees plaintext; everything right of it must not.

```
 creator client ─┐                          ┌──────────── server ─────────────┐
                 │  ciphertext, header,     │ Axum: limits, capabilities,     │
                 ├─ verifiers ─────────────▶│ lifecycle, assets               │
 recipient ──────┤                          │ SQLite: ciphertext + metadata   │
                 │◀─ ciphertext on proof ───│ operator CLI: backup, moderation│
                 │   of the reveal token    └─────────────────────────────────┘
   plaintext, keys, link secret, password never cross this line
```

## Adversaries and controls

| Adversary / threat | Controls | Verified by | Residual risk |
| --- | --- | --- | --- |
| **Database or backup leak** | AES-256-GCM ciphertext; no keys, secrets or content metadata stored; verifiers only (`SHA-256`, domain-separated); backups compacted so freed pages of deleted pastes are not copied | `db_no_plaintext.rs` (CI gate), backup tests, `smoke.sh` greps DB and backup for secrets | Padded sizes (order of magnitude), timestamps and lifecycle flags are visible. Reports contain personal data, creation token labels may. |
| **Curious or compelled operator** | Same as above; operator tools work on ids and metadata only, never decrypt | — (by construction) | Operator sees who creates when (via logs on the proxy, not in CapsuleBin), and sizes; per database creation token the day it was last used, never which capsules it created. |
| **Malicious or compromised server shipping modified JavaScript** | Embedded assets, strict CSP, no third-party resources; the CLI as a client that does not depend on served code; reproducible web assets, so a tag's client can be rebuilt and compared with what a server ships | CSP asserted on every response (`smoke.sh`); two web builds compared byte for byte (`scripts/reproducible-web.sh`, CI) | **Not prevented.** A compromised server can exfiltrate keys from web users. This is the model's documented limit (ADR-001). |
| **Network observer** | HTTPS (at the reverse proxy, with HSTS); the fragment is never sent; `Referrer-Policy: no-referrer`; ciphertext padded (PADMÉ) | Security headers in `smoke.sh`, padding tests and golden vectors | Server IP, timing and padded sizes are observable. |
| **Link preview bots and scanners** | A share link `GET /p/{id}` (and `/{lang}/p/{id}` in every other language) serves the same static shell for every id; a path under the default language's prefix answers a `302` to the path without it, copied without inspecting the id; the server never reads `Accept-Language`; nothing looks the id up, retrieval is an explicit `POST` with the reveal token | `view_shell_is_identical_for_every_id`, `the_prefix_of_the_default_language_is_redirected_away`, `smoke.sh` | Scanners that execute JavaScript and hold the full link (fragment included) can consume a burn capsule. |
| **Someone who learns a paste id** (logs, history, proxy, report form) | Descriptor, retrieval and delete each need a capability derived from the link (describe token, reveal token, delete secret); ids are 128-bit random; the access log records the matched route's template (`/api/v1/pastes/{id}/retrieve`), never the request path | `the_descriptor_needs_a_capability`, `logging.rs` (CI gate), incl. `random_paths_log_only_templates_assets_or_unmatched` (seeded random paths through the real stack) | None: without the link the id answers like an unknown one. |
| **Existence probing** (does id X exist?) | Every endpoint taking an id requires a capability; unknown, expired, consumed, disabled, deleted and wrong-capability answer identically; the check runs against a dummy verifier for unknown ids, and the schema cannot hold a paste without a describe verifier (`NOT NULL`); reports are answered identically whether or not the id exists or a report ceiling was reached; create answers the same `409 id_conflict` for a live row, a tombstone and a retired id, so it does not tell them apart | `the_descriptor_needs_a_capability`, `wrong_token_and_unknown_id_are_indistinguishable`, `moderated_pastes_look_exactly_like_unknown_ones`, report tests incl. `dropped_reports_answer_like_stored_ones`, `a_purged_id_cannot_be_created_again`, `a_paste_without_a_describe_verifier_is_refused` (`db.rs`), `smoke.sh` | Anyone allowed to create (every client in `public` mode, token holders in `token` mode) can test whether one specific id is taken or was ever used: creating it answers `409` (ADR-011). Without permission to create, nothing changes. Small timing differences (e.g. a stored vs. an unstored report); mitigated by rate limits and the id space. |
| **Link re-seating** (a link holder recreates a purged capsule's id with the same link secret, so the old link opens different content; reports and moderation by id would attach to that new capsule) | Ids are never freed: every row deleted from `pastes` (the three retention rules, or any other delete) leaves its id in `retired_ids` through a database trigger, and create refuses a retired id in the same statement as the insert with the ordinary `409 id_conflict`; delete, burn and moderation keep a tombstone row anyway. `restore` retires every id of the replaced database (rows and retired ids) that the backup does not hold as a row, and a capsule both hold keeps the replaced database's burned, deleted or disabled state (never its ciphertext), so a restore never makes a burned or deleted capsule readable again or lifts a moderation. Reports about a purged id show it as `gone`, moderation answers that there is no such paste, and a new report is not stored | `a_purged_id_cannot_be_created_again` (one case per retention rule), `a_report_on_a_purged_paste_never_reaches_a_new_capsule` (`retired_ids.rs`); `a_capsule_pruned_by_the_binary_stays_gone_for_reports_and_moderation` (`retired_ids_acceptance.rs`, real binary); `deleting_a_row_retires_its_id`, `retired_ids_outlive_every_retention_rule` (repository); `purged_fixture_ids_stay_retired` (`upgrade.rs`); `restore_retires_ids_missing_from_the_backup`, `restore_carries_many_ids_over`, `restore_keeps_burns_deletions_and_moderation_after_the_backup` (`backup/tests.rs`) |  A restore whose replaced database cannot be read (corrupt, or a `-wal` without `-shm`) installs the backup with a warning, and the replaced database's ids missing from the backup can be used again; capsules it burned, deleted or disabled after the backup are available again. A link still does not commit to its content: whoever controls the server can serve other ciphertext under an id. |
| **Brute force of ids, reveal tokens or delete secrets** | 128-/256-bit randomness; failed attempts are optionally throttled per client before any lookup | `tests/rate_limits.rs`, `smoke.sh` over a real socket | None practical at these key sizes. |
| **Online password guessing** (link leaked, password not) | Every guess needs a retrieve with a reveal token derived from it; retrieves of one paste that prove the link but fail the reveal token are limited from any address (`invalid_capability_per_paste`, on by default), checked and charged atomically so parallel guesses cannot exceed the burst; keyed on the id the retrieve handler looked the paste up by, so every spelling of the id in the URI (percent-encoded in upper- or lower-case hex, fully or partly) shares one budget; a password budget is never evicted from the limiter's memory, so flooding it cannot reset one, and with the table full the pastes it has no slot for share one overflow budget with the per-paste spec, charged for correct and wrong attempts alike, so a full table never answers by the password (see the limiter-state row) | `tests/rate_limits.rs`, `password_budgets_survive_saturation`, `untracked_pastes_share_the_overflow_budget_when_saturated` (`api/rate_limit.rs`), `a_saturated_retrieve_answers_correct_and_wrong_passwords_alike` (`api/rate_limit.rs`, through the router), `parallel_password_guesses_cannot_exceed_the_per_paste_burst`, `password_attempts_share_one_budget_across_id_spellings`, `password_attempts_across_id_spellings_are_limited_under_concurrency` | Roughly 14 000 guesses a day per capsule at the default; weak passwords still fall eventually. |
| **Blocking a capsule by its id** (id leaked, link not) | The per-paste limit counts only retrieves that prove the link with the describe token, and is checked only after that proof; describe and delete never touch it; this holds for every spelling of the id | `a_caller_with_only_the_id_cannot_block_a_capsule`, `a_caller_with_only_the_id_cannot_drain_the_budget_in_any_spelling`, `password_attempts_on_one_paste_are_limited_by_default_from_any_address` | A link holder can keep the password limit drained - but could retrieve or burn the capsule anyway. |
| **Offline password guessing** | The link secret is a mandatory second factor; PBKDF2 (600 000 iterations by default, versioned, never fewer than 100 000 accepted); no password verifier in the public header; ciphertext only after a correct reveal token | Golden vectors, `public_header` tests | Someone who has the link **and** the ciphertext can guess offline. Weak passwords fall. |
| **A link issuer guessing the recipient's password offline** (a hostile link names its own server and KDF parameters; the reveal token derived from the password goes to that server) | Clients refuse a public header with fewer than 100 000 PBKDF2 iterations, a non-integer count or a password salt other than 16 bytes, before a password is asked for or a reveal token derived (web and CLI share the parser; reported as an invalid capsule). The CLI uses `CAPSULEBIN_PASSWORD` only for links to the server named with `get --server`/`CAPSULEBIN_SERVER` (scheme, host, port and path compared); for any other link it stops non-interactively or prompts | `public_header.test.ts`, `properties.test.ts`, `public_header` vectors in `golden-vectors.test.ts`, `open.test.ts` (no password hook, no retrieve), `cli.test.ts` (origin match and mismatch, exit codes `5` and `8`) | A password typed into the prompt or given with `--password-file` is sent (as a reveal token) to whatever server the link names; at 100 000 iterations a weak password still falls to an issuer who guesses offline. |
| **Capabilities over cleartext or redirected transport** (a CLI pointed at `http://`, a proxy or attacker answering with a redirect) | The CLI refuses plain `http://` for `put --server` and the link of `get`/`delete` except on `localhost`, `127.0.0.0/8` and `[::1]`, unless `--allow-http`/`CAPSULEBIN_ALLOW_HTTP=1`; the core API client (web and CLI) follows no redirect on any API request and does not show the `Location`; `put` does not retry a refused redirect | `redirect.test.ts` (two real servers: the redirect target receives nothing), `cli.test.ts` (HTTP policy, redirect exit code `7` with one create request) | `--allow-http` sends capabilities unencrypted, by the user's choice. Names under `.localhost` and private networks need the opt-in like any host. |
| **Links exposed on the creator's or recipient's machine** (argv visible in `ps`, shell history, logs that capture stderr or JSON) | `get`/`delete` read the link from stdin (`-`) or `--link-file`; `put --delete-link-file` writes the management link to a new owner-only (`0600`) file, created exclusively before the upload, and then leaves it out of stderr and the JSON output, also after a failure; error messages never quote what was read, and a link source whose first line exceeds 16 384 bytes is refused naming only the source | `cli.test.ts` (round trips, usage errors without input, file mode, existing file refused, file removed only when it could not be written, kept after a failed create, empty `--link-file`, first-line limit), `smoke.sh` (no `#v1.` on stderr of `put`/`get`/`delete`, mode `600`) | A link given as an argument still works and is still exposed; the share link is still printed on stdout. |
| **A creation token sent to the wrong server** (a script or CI job sets `CAPSULEBIN_TOKEN` for one instance and runs `put --server` against another, perhaps hostile one) | With `CAPSULEBIN_SERVER` set, `put` treats `CAPSULEBIN_TOKEN` as that server's token: for another `--server` (scheme, host, port and path compared, trailing slashes ignored), or when `CAPSULEBIN_SERVER` is not a usable URL, the token is withheld and stderr says so, naming both bases, never the unusable value; an empty `--token-file ""` is a usage error, not a fallback to the variable | `cli.test.ts` (`CAPSULEBIN_TOKEN and CAPSULEBIN_SERVER`: mismatch, trailing slash, no `CAPSULEBIN_SERVER`, `--token-file`, unusable URL, exit `6`; `empty path options`) | Without `CAPSULEBIN_SERVER` the token goes to whichever server `--server` names, so that existing scripts keep working. `--token-file` is sent to any server. |
| **The creation token in the browser** (a script on the instance's origin, someone with access to the browser profile, an invitation link that leaks, the token reaching other requests; ADR-018) | Same-origin script only: strict CSP, Trusted Types, no third-party resources, no inline script; the invitation token sits in the URL fragment, which browsers never send, and the create page removes it from the address bar and the current history entry with `history.replaceState` before rendering, in every mode, storing it only in `token` mode; the token is sent only as `Authorization: Bearer` of the create request, never on describe, retrieve or delete, never in a URL or body; "Remember in this browser" can be unchecked (held for the page only, storage untouched) and "Forget" removes it; a token the server refuses is removed from storage at once; only 1–1024 visible ASCII characters are accepted | `creation-token.e2e.ts` (bearer on create only over a create → open → delete flow, invitation links on `/`, `/de/`, `/en/` with an empty address afterwards, remember off, forget, refused token, public and disabled instances), `creation-token.test.ts` (fragment parser, `replaceState`, storage that throws), `create-page.test.ts`, `the_create_page_names_the_creation_mode` (`http.rs`) | Whoever has the browser profile or the invitation link has the token until the operator revokes it or removes its hash. A script that runs on the origin despite the CSP (or modified JavaScript served by a compromised server) can read a stored token. An invitation link is a credential in a URL: whoever reads it where it was sent (chat, mail, a previewer that follows links with their fragment) can use it. |
| **A leaked or withdrawn creation token** (a token that should no longer create, a revocation undone by a restore, a token guessed from the database) | Database tokens are revoked with `capsulebin token revoke` while the server runs; authorization reads the active tokens on every create (no cache), so a revocation applies from the next request, through a partial index over the active rows, so a long revocation history does not slow every create; revocation is final and revoked rows are never deleted; the bearer is compared against the configured and every active database verifier in constant time without an early return (`capability::matching_index`), never selected by a `WHERE verifier = ?` lookup; a revoked, an unknown and a missing token get the same `401`, decided before the body is read; a failed read of the tokens is `500`, never `401` (which would make a browser forget a valid token); `restore` carries the replaced database's tokens and revocations into the restored one, matched by hash; only hashes are stored (`Verifier::for_creation_token`, 32 random bytes per generated token) | `database_and_configured_tokens_are_accepted_alike`, `database_tokens_apply_from_the_next_create`, `an_unreadable_token_table_is_an_internal_error`, `an_unauthorized_create_never_reads_the_body` (`api.rs`); `matching_index_*` (`domain/capability.rs`); `database_creation_tokens_store_only_their_verifier` (`db_no_plaintext.rs`); `a_running_server_follows_issued_and_revoked_tokens`, `revoke_is_final` (`creation_tokens_acceptance.rs`, real binary); `active_tokens_are_read_through_the_partial_index` (repository); `restore_carries_creation_tokens_matched_by_verifier`, `restore_over_a_database_missing_a_table_carries_nothing` (`backup/tests.rs`), `restore_keeps_creation_tokens_and_revocations_made_after_the_backup` (`restore_acceptance.rs`) | A token works until it is revoked: there is no expiry. A configured hash stays valid until it is removed and the server restarted. A restore over a current database it cannot read, or one without `retired_ids` or `creation_tokens` (a warning), carries nothing: tokens the backup holds unrevoked are active again until revoked once more. |
| **XSS through Markdown or code** | Only Markdown renders HTML: marked → DOMPurify allowlist → link policy; highlight.js escapes; strict CSP; Trusted Types required; no inline scripts or styles | `xss.test.ts`, `trusted-html-usage.test.ts`, CSP in `smoke.sh`; browser tests (`src/server/web/e2e`) in Chromium, Firefox and WebKit with hostile Markdown, an XSS canary and every CSP/Trusted Types violation failing the test | Sanitizer or browser bugs. |
| **Script through the operator's legal texts** (`[legal]`, ADR-015) | The operator is trusted, but the text lands on every visitor's screen: rendered at startup without raw HTML or images, links limited to http(s), mailto, tel and local paths, `url` values to absolute http(s) URLs and single-slash paths; strict CSP on the pages | `legal/markdown.rs` tests (raw HTML, unsafe links, images, escaping), `legal/tests.rs` (URL allowlist), `legal.e2e.ts` under the CSP guard | A misleading but harmless text; the operator controls the instance anyway. |
| **Malicious capsule** (crafted by a creator to attack the recipient's client) | AES-GCM authenticates the whole container; strict, length-checked parser that never allocates from unchecked sizes; files are only downloaded, never previewed. CLI `get`: item content is only ever written to files, never to stdout, so it never reaches a terminal as output; every diagnostic on stderr (manifest text in errors, file and directory names) escapes all control characters, newlines included, and `--json` writes DEL and C1 as `\u00NN`; file names keep only the last path component and lose C0, DEL and C1; every file is created exclusively (`wx`) with mode `0600`, so an existing entry at the name — file, directory, symlink, dangling or not — is never opened, followed or replaced: the item takes the next free name; new directories are `0700`; without `-o` or `--here` every capsule, a single item included, is written into a new `0700` directory `capsule-<date>-<id prefix>`, so a sender cannot plant a file such as `.envrc`, `Makefile` or `conftest.py` in the directory `get` runs in; `-o ""` is a usage error, not the current directory; a failed write removes the files and the new directory this run created | Property tests on the decoder (arbitrary, corrupted, truncated input); `escape.test.ts` (every code point and byte in U+0000–U+00FF, random strings); `cli.test.ts` (`file output`: modes under umask `000`, existing files, symlinks and directories at the name, no free name, failed write, a single item in a new owner-only directory and nothing in the working directory, `--here`/`-o`, empty stdout; `terminal output`: escaped server problems, `created`/`wrote` lines, JSON bytes) | Downloaded files are as dangerous as any download; opening a written file (`cat` included) passes its bytes on unchanged. Bidi and invisible characters (U+202A–U+202E, U+2066–U+2069, zero-width) are not escaped in diagnostics and can still make text read differently than it is. A process killed during a write can leave a partial owner-only file under the item's name. File modes are not asserted on Windows. With `--here` or `-o DIR` the sender's file names land in that directory (still never replacing an entry). |
| **A malicious server's messages** (problem `title`/`code` crafted to forge terminal output or extra `capsulebin:` lines) | The CLI escapes every control character of server text on stderr, newlines included, whether or not stderr is a terminal; `--json` writes DEL and C1 as `\u00NN`; the last-resort message in `main.ts` goes through the same function | `cli.test.ts` (`terminal output`: 4xx and 5xx with ESC, newline and U+009B in title and code; JSON error bytes), `escape.test.ts` | Printable text from the server is shown as it is. |
| **A hostile or broken server exhausting a client** (a link to an instance that answers with an endless or huge body, never answers, or stalls mid-body; a capsule padded beyond the format) | In the core API client (web and CLI) oversized responses are cut off: every body, error bodies included, is read as a stream and counted whatever `Content-Length` says, at most 64 KiB, a successful retrieve at most the base64url of the largest valid ciphertext (`MAX_CAPSULE_BYTES` + 16) plus 1 KiB; above that the stream is cancelled (`response_too_large`). Each request has a total deadline (30 s for describe and delete, 10 min for create and retrieve), and a body that delivers no bytes for 30 s is cancelled (`timeout`); both are status `0` like a network error, so the web client shows its network error text and the CLI exits `7`. `openPaste` refuses a ciphertext above `MAX_CAPSULE_BYTES` + 16 before decrypting, and the capsule decoder refuses input above `MAX_CAPSULE_BYTES` before scanning it. `put` retries a timeout with the same sealed paste, never an oversized response | `limits.test.ts` (`oversized responses are cut off` for every endpoint and error statuses, without, with a wrong and with a correct `Content-Length`; `a capsule at the size limit still opens`; `requests time out` with fake timers), `limits.acceptance.test.ts` (an error body of exactly 64 KiB read, one byte more cut off; a create not cut off at 30 s; a stalled describe or error body times out), `capsule.test.ts`, `open.test.ts` (no decrypt call), `errors.test.ts` (web text), `cli.test.ts` (exit `7`, reasons, retry counts) | A client still holds up to about 13.4 MiB of a retrieve answer in memory, and a server can keep a recipient waiting up to 10 minutes. A burn capsule whose retrieve times out after the server answered is consumed without being shown. The report page's own requests (same origin only) are not bounded this way. |
| **A local input too large for a capsule** (`put` given a huge file, a pipe that never ends or a special file like `/dev/zero`) | `put` sums the sizes of the regular input files and refuses a sum above `MAX_CAPSULE_BYTES` before reading any; then it reads all inputs, stdin included, within one budget of `MAX_CAPSULE_BYTES` and stops at the first byte beyond it. Exit code `2`, a message naming the limit in bytes, nothing sent | `cli.test.ts` (`put refuses inputs above the capsule limit before reading them`, `put stops reading at the capsule limit`: endless stdin, `/dev/zero`, file plus stdin) | — |
| **A terminal left broken or a guarded request sent anyway** (Ctrl-C or EOF at a CLI prompt) | Prompts use a real output stream; readline restores echo and line mode on an answer, Ctrl-C and EOF; Ctrl-C (`interrupted`) and EOF (`input_closed`) end with exit code `8` before the create or retrieve the prompt guards | `terminal.test.ts` on a python3 pseudo-terminal against the bundled CLI: hidden password (typed marker never shown), burn confirmation `y`/`n`/Ctrl-C/EOF, Ctrl-C and EOF at the password prompt of `get`, Ctrl-C at the first one of `put`, request counts at the fake API, `stty -a` after every run | A process killed with `SIGKILL` at a prompt cannot restore the terminal. |
| **Burn races** (two recipients, or a scanner and a recipient) | `BEGIN IMMEDIATE` burn transaction with an affected-row check; rate-limited and unauthorized requests never reach it | Repository and HTTP-level race tests, 20-connection race in `smoke.sh` | "Burned" means first *authorized retrieval*, not "read by a human". |
| **I/O amplification by unauthorized requests** | Descriptor, retrieve and delete check capabilities against metadata only; the payload is read after authorization | `metadata_lookups_do_not_read_the_payload` | — |
| **Storage and resource abuse** | Token creation mode by default; create decides the creation capability from the request head (mode, `Authorization`) before a body byte is read, and a disabled report endpoint answers `404 reports_disabled` unread; body and plaintext limits: create up to `max_body_bytes`, describe, retrieve and delete 4 KiB, reports 32 KiB, each `413 payload_too_large` for a declared and a streamed body; per-client request rates, daily byte quota, concurrent-upload cap; retention purge; open reports (`open` or `reviewing`) capped per capsule (`abuse.max_open_reports_per_paste`, default 10) and per instance (`abuse.max_open_reports`, default 1000), checked and inserted in one statement, a report above a ceiling dropped with the same `202`; a create that collides with a stored id is decided from that row's metadata (verifiers, public header, payload size, lifecycle), and its ciphertext is loaded only when the request can still be an identical replay, so a small request with a taken id cannot make the server read a payload of up to 10 MiB | `tests/rate_limits.rs`, `api.rs` size tests, `a_conflict_is_decided_before_the_payload_is_read` (`api/pastes/handlers.rs`, payload reads counted), `a_replay_must_match_every_capability_and_option` (`api.rs`), `an_unauthorized_create_never_reads_the_body`, `a_streamed_create_above_the_body_limit_is_refused`, `proof_routes_have_a_small_body_limit` (`api.rs`); `disabled_reports_never_read_the_body`, `reports_have_a_small_body_limit`, `dropped_reports_answer_like_stored_ones` (`abuse.rs`); `open_reports_are_capped_per_paste_and_globally`, `the_report_ceiling_holds_under_concurrency` (abuse repository); `reports_list_starts_with_the_open_reports_and_both_ceilings`, `a_report_ceiling_below_one_stops_the_binary` (`report_ceilings_acceptance.rs`, on the binary) | Public-mode instances remain abusable within the limits. Unauthorized creates still pass the byte quota and concurrency checks before they are refused. No server-side body timeout and no instance-wide upload budget: slow or many parallel bodies are left to the reverse proxy. Reports about one capsule, or junk about many, can fill the ceilings and crowd out later genuine reports until an operator closes them. |
| **Illegal content** | Notice and action: report by id, operator disables or deletes without decrypting; audit trail | `tests/abuse.rs`, `smoke.sh` | No preventive moderation under zero knowledge. |
| **A key pasted into a report** (a reporter copies the whole share or management link into the description or contact) | The report page sends only the id from the id field (the fragment is cut off first) and refuses a description or contact containing `#v1.` before any request exists: no `POST`, a message in the page language, focus on the first field concerned, the text left for the reporter to correct. The detection rule is one core function (`containsKeyFragment` in `src/core/src/links.ts`), exactly the server's rule; the server refuses such text too, for other clients | `containsKeyFragment` tests (`src/core/tests/links.test.ts`), `report-page.test.ts` (no `POST`, message, focus, text kept), `the report form refuses a link with its key in the description or contact` (`capsule.e2e.ts`, requests counted in the browser), `a_report_containing_a_key_is_refused` and `accepted_reports_carry_no_key_and_no_control_characters` (server) | A bare key without `#` (`v1.…` or the base64url secret alone) is not detected, in the browser or on the server. ## Explicit non-goals

- Protection against a fully compromised server for **web** users (see above).
- Physical erasure. Removing burned, deleted and purged ciphertext happens in four distinct steps:
  - logically it is unavailable at once, when the delete, burn or purge commits;
  - in the database file SQLite's `secure_delete` overwrites it with zeros, once a checkpoint has
    copied the zeroed pages from the write-ahead log into the file;
  - WAL frames written before the delete can keep the old ciphertext after that checkpoint, until
    later writes reuse them or the WAL is truncated; an ordinary checkpoint does neither;
  - the WAL is truncated only on a `wal_checkpoint(TRUNCATE)`, when the last connection closes, or
    down to the 64 MiB `journal_size_limit` when it is reset, so up to that much of old frames can
    remain.

  `secure_delete.rs` checks the file and the WAL after a `TRUNCATE` checkpoint, not what an
  ordinary checkpoint leaves. Beyond the database file nothing is promised: WAL frames as above,
  the filesystem, SSD wear levelling and older backups may still hold ciphertext. Of a purged
  capsule the id stays in `retired_ids` for good (see link re-seating).
- Anonymity: CapsuleBin does not hide who talks to the server.
- Preventive content scanning, proof of reading, or recovery of lost links.
